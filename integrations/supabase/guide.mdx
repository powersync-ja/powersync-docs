## Architecture

<Frame caption="Supabase + PowerSync architecture">
  ![Diagram of the PowerSync Service syncing data from Supabase Postgres to SQLite in the app, and the app uploading writes to Supabase through the Supabase client library](/images/integration-guides/supabase/powersync-docs-diagram-supabase-integration.png)
</Frame>

The PowerSync Service replicates data from Supabase Postgres and syncs it to each client's SQLite database, based on your Sync Streams. When the app writes to SQLite, the PowerSync SDK also adds the change to an upload queue. While the device is online, the SDK calls the app's `uploadData()` function, which sends queued changes to Supabase through the Supabase client library. For more on how PowerSync works, see the [Architecture Overview](/architecture/architecture-overview).

### Create the Demo Database Schema

The demo app uses two tables, `lists` and `todos`. Run the following SQL to create them:

```sql
create table
  public.lists (
    id uuid not null default gen_random_uuid (),
    created_at timestamp with time zone not null default now(),
    name text not null,
    owner_id uuid not null,
    constraint lists_pkey primary key (id),
    constraint lists_owner_id_fkey foreign key (owner_id) references auth.users (id) on delete cascade
  ) tablespace pg_default;

create table
  public.todos (
    id uuid not null default gen_random_uuid (),
    created_at timestamp with time zone not null default now(),
    completed_at timestamp with time zone null,
    description text not null,
    completed boolean not null default false,
    created_by uuid null,
    completed_by uuid null,
    list_id uuid not null,
    constraint todos_pkey primary key (id),
    constraint todos_created_by_fkey foreign key (created_by) references auth.users (id) on delete set null,
    constraint todos_completed_by_fkey foreign key (completed_by) references auth.users (id) on delete set null,
    constraint todos_list_id_fkey foreign key (list_id) references lists (id) on delete cascade
  ) tablespace pg_default;

-- Grant Data API access so supabase-js can read and write these tables.
grant select, insert, update, delete on public.lists to authenticated;
grant select, insert, update, delete on public.todos to authenticated;
grant select, insert, update, delete on public.lists to service_role;
grant select, insert, update, delete on public.todos to service_role;

-- Enable Row Level Security and add policies so each user can only access their own data.
alter table public.lists enable row level security;
alter table public.todos enable row level security;

create policy "owned lists" on public.lists
  for all to authenticated
  using (auth.uid() = owner_id);

create policy "todos in owned lists" on public.todos
  for all to authenticated
  using (
    auth.uid() in (
      select lists.owner_id from public.lists where lists.id = todos.list_id
    )
  );
```

Sync Streams, which you configure later, control which rows sync to each client. They usually mirror your RLS policies. See [RLS and Sync Streams](/integrations/supabase/rls-and-sync-streams).

<Tabs>

    You deploy this configuration together with your Sync Config in the next step.
  </Tab>

### Configure Sync Streams

[Sync Streams](/sync/streams/overview) define which data syncs to which users' devices. In the demo app, each user syncs their own lists and to-dos. Use the following Sync Config:

```yaml
config:
  edition: 3
streams:
  user_data:
    auto_subscribe: true
    queries:
    - SELECT * FROM lists WHERE owner_id = auth.user_id()
    - SELECT todos.* FROM todos INNER JOIN lists ON todos.list_id = lists.id WHERE lists.owner_id = auth.user_id()
```

<Tabs>
  <Tab title="Web UI">
    1. In the [PowerSync Dashboard](https://dashboard.powersync.com/), select your project and instance and go to the **Sync Streams** view.
    2. Replace the contents of the editor with the Sync Config above.
    3. Click **Validate** and fix any errors.
    4. Click **Deploy**.
  </Tab>
  <Tab title="CLI">
    Replace the contents of `powersync/sync-config.yaml` with the Sync Config above. Then deploy the full configuration, which includes the database connection, client auth, and Sync Config:

    ```bash
    export POWERSYNC_DATABASE_PASSWORD=<powersync_role password>
    powersync deploy
    ```
  </Tab>
</Tabs>

## Optional: Add Sample Data for New Users

If you share the demo app with other people, you can add sample data for each new user, so that they don't start with an empty screen. The following trigger creates a list with two to-dos when a user signs up. Run it like the other SQL in this guide. See [Supabase: Managing User Data](https://supabase.com/docs/guides/auth/managing-user-data#using-trigger).

```sql
create function public.handle_new_user_sample_data()
returns trigger as $$
declare
  new_list_id uuid;
begin
  insert into public.lists (name, owner_id)
    values ('Shopping list', new.id)
    returning id into new_list_id;

  insert into public.todos(description, list_id, created_by)
    values ('Bread', new_list_id, new.id);

  insert into public.todos(description, list_id, created_by)
    values ('Apples', new_list_id, new.id);

  return new;
end;
$$ language plpgsql security definer;

create trigger new_user_sample_data after insert on auth.users for each row execute procedure public.handle_new_user_sample_data();
```

## Troubleshooting

### Uploads Fail With Error `42501`

If changes from the app don't reach Supabase and your app logs error `42501`, the Data API rejected the upload. Check the error message:

- **`permission denied for table`:** The `authenticated` role has no grant on the table. Grant access to each table that your app writes to, for example `grant select, insert, update, delete on public.lists to authenticated;`.
- **`new row violates row-level security policy`:** An RLS policy rejected the write. Check that the row belongs to the signed-in user, for example that `owner_id` matches the user's ID.

The demo [schema SQL](#create-the-demo-database-schema) shows both the grants and the RLS policies.

### Disk Fills Up on an Idle Project

On Supabase projects with a small disk, such as Free plan projects, Postgres can keep a growing amount of write-ahead log (WAL) while PowerSync is connected, even when the database is idle. This can fill the disk.

Check `max_wal_size` and `max_slot_wal_keep_size` with `SHOW max_wal_size;` and `SHOW max_slot_wal_keep_size;`. If either value is more than half of your disk size, lower that value. For example, for a 2 GB disk, set both to 1 GB:

```bash
supabase --experimental --project-ref <project-ref> postgres-config update --config max_wal_size=1GB
supabase --experimental --project-ref <project-ref> postgres-config update --config max_slot_wal_keep_size=1GB
```

A lower `max_slot_wal_keep_size` leaves less room for replication lag. If the lag exceeds it, Postgres invalidates PowerSync's replication slot. See [Recovering from an Invalidated Slot](/configuration/source-db/postgres-maintenance#recovering-from-an-invalidated-slot).

### Unused Replication Slots

If you stop or deprovision your PowerSync instance, its replication slot stays in your Supabase database and keeps WAL. Drop slots that you no longer need. See [Logical Replication Slots](/configuration/source-db/postgres-maintenance#logical-replication-slots).
