---
title: "Choosing Your Setup"
description: "Pick the write path setup that fits your backend: Supabase, your existing API, the reference write implementation, or a write endpoint in your own stack."
---

Each option below gives you a mutation uploader and a write endpoint. They differ in what you already have and what you need to deploy.

| Your setup | Write endpoint | Mutation uploader | Guide |
| --- | --- | --- | --- |
| You use Supabase, and related changes don't have to be saved atomically (together or not at all). | None: Supabase's Data API, checked by your RLS policies | Supabase uploader | [Supabase: PostgREST Route](/handling-writes/write-path/supabase-postgrest) |
| You use Supabase, and related changes must be saved atomically (together or not at all). | Reference write endpoint, deployed as an Edge Function | Reference uploader | [Supabase: Edge Function Route](/handling-writes/write-path/supabase-edge-function) |
| You already have an API that your app uses for writes. | Your existing API | One you write for your API | [Use Your Existing API](/handling-writes/write-path/existing-api) |
| You don't have a write endpoint, and a Node.js backend works for you. | Reference write endpoint (Node.js) | Reference uploader | [Reference Write Implementation](/handling-writes/write-path/reference-write-implementation) |
| You don't have a write endpoint, and want it in your own backend stack. | One you build that follows the reference API contract | Reference uploader | [Build Your Own Write Endpoint](/handling-writes/write-path/build-your-own-write-endpoint) |

Whichever option you choose, [Write Path Concepts](/handling-writes/write-path/concepts) covers what every write endpoint must do: authenticate writes, apply them before responding, and handle failures without blocking the upload queue.
