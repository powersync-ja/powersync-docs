PowerSync syncs data from your source database to your app's local SQLite database. Your app writes to this local database, and the client SDK records changes to synced tables in an ordered **upload queue**.

Your backend applies the queued changes to your source database, so your business logic, such as validation and authorization, can run before a change is stored.

The two orange boxes with dashed borders are the parts you integrate: an `uploadData()` function in your app's backend connector and a **Write API** in your application backend.

You can use an existing API, Supabase's PostgREST API, or the reference write implementation. Your write API is responsible for [authenticating and authorizing writes](/handling-writes/write-path/concepts#authenticating-writes).

## How a Write Reaches Your Source Database

You implement steps 3 and 4. The client SDK and the PowerSync Service handle the other steps.

1. When your app writes to a synced table in the client-side SQLite database, the client SDK also adds the write to the [upload queue](/architecture/client-architecture#writing-data-via-sqlite-database-and-upload-queue).
2. The client SDK calls the `uploadData()` function in your [backend connector](/configuration/app-backend/client-side-integration#backend-connector) to upload the queued writes. You never call `uploadData()` directly. See [When `uploadData()` is Called](/configuration/app-backend/client-side-integration#when-uploaddata-is-called).
3. Your `uploadData()` function sends the queued writes to your write API. After a successful response, your function calls `complete()` on the transaction or batch it sent, which removes those writes from the upload queue. For failed requests, see [Error Handling](/configuration/app-backend/client-side-integration#error-handling).
4. Your write API applies the writes to your source database before responding. See [Applying Writes Before Responding](/handling-writes/write-path/concepts#applying-writes-before-responding) for the reason.
5. The PowerSync Service replicates the changes from your source database and syncs them to every client whose [Sync Streams](/sync/streams/overview) include the changed rows.

Your app sees its own change immediately after step 1, because it reads from the local database. Other users' apps see it after step 5. If your write API rejects or changes the write, the synced result replaces the local change. While the device is offline, steps 2 to 5 wait until it reconnects.
