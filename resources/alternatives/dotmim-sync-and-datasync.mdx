[Dotmim.Sync](https://dotmimsync.readthedocs.io/) is an open-source .NET library that syncs rows between a server database and client databases. The client app starts each sync session by calling `SynchronizeAsync()`. On SQL Server, Dotmim.Sync detects changes with SQL Server Change Tracking, or with its own triggers and tracking tables.

[CommunityToolkit.Datasync](https://communitytoolkit.github.io/Datasync/) is part of the .NET Community Toolkit and was previously known as Azure Mobile Apps. Your ASP.NET Core API hosts its table controllers. The app uses an EF Core `OfflineDbContext` that stores data in SQLite and sends or fetches changes when the app calls `PushAsync()` or `PullAsync()`.

PowerSync syncs data from your backend database into a SQLite database inside your app. The app reads and writes that local database directly, so it responds instantly and keeps working without a network connection. PowerSync syncs changes in both directions when the app is connected. On SQL Server, the PowerSync Service reads changes through Change Data Capture (CDC).

This comparison is based on each product's documentation and source code, and on building the same SQL Server, ASP.NET Core, and .NET MAUI app with each of the three tools. See [Migrating a SQL Server and .NET MAUI App to Offline-First](/migration-guides/sql-server-maui) for the PowerSync version of that app.

## How Server Changes Are Captured

The PowerSync Service reads changes from SQL Server through [Change Data Capture (CDC)](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server). A SQL Server Agent job copies each change from the transaction log into change tables, and the Service polls those tables. Your tables are unchanged. Setup needs CDC on the database and on each synced table, a running SQL Server Agent, a `powersync_user` login, and a `_powersync_checkpoints` table. On Azure SQL Database, the CDC jobs are managed for you. See [SQL Server](/configuration/source-db/setup#sql-server) for the steps.

CDC captures every committed change. Writes made directly with SQL, for example by a back-office system, reach devices with no change to that system.

Dotmim.Sync's `SqlSyncChangeTrackingProvider` uses SQL Server [Change Tracking](https://dotmimsync.readthedocs.io/ChangeTracking.html). You turn on Change Tracking for the database, and Dotmim.Sync turns it on for each synced table. Dotmim.Sync's other SQL Server provider, `SqlSyncProvider`, adds a tracking table and triggers to each table instead. Both providers [provision](https://dotmimsync.readthedocs.io/Provision.html) stored procedures, table types, and scope tables in your database. Dotmim.Sync adds no columns to your tables, and it picks up changes made directly with SQL.

Datasync tracks changes with metadata on each row. Each synced entity has `Id`, `UpdatedAt`, `Version`, and `Deleted` properties. On an existing table, you add those columns or map them onto existing columns with EF Core. On SQL Server, the [Datasync docs](https://communitytoolkit.github.io/Datasync/in-depth/server/db/azuresql/) add a trigger that sets `UpdatedAt` on every insert and update, so changes made directly with SQL are also picked up. The client pulls the rows whose `UpdatedAt` is later than the newest row it already has.

Datasync doesn't send hard deletes to devices. To sync deletes, you [enable soft delete](https://communitytoolkit.github.io/Datasync/in-depth/server/), which marks rows as deleted, and run a separate job to purge them. Other systems that delete rows with SQL then need to set the `Deleted` column instead.

## How Data Is Stored on the Client

The PowerSync client SDK manages a SQLite database on the device. Your app queries it with SQL. [Watch queries](/client-sdks/watch-queries) rerun when a local write or a sync changes a table that the query reads, so the UI updates without a manual reload.

Dotmim.Sync creates a SQLite database that mirrors the server tables on the first sync. Your app queries it with `Microsoft.Data.Sqlite`. Dotmim.Sync has no watch queries, so your app queries again after each sync and each local write.

Datasync stores data in SQLite through EF Core, and your app queries the `OfflineDbContext` with LINQ. Your entities are typed classes on both the server and the client. Datasync has no watch queries.

## How Writes Work

All three tools save the user's change locally first, so the app shows it immediately. They differ in how the change reaches SQL Server:

| Step | **PowerSync** | **Dotmim.Sync** | **Datasync** |
| --- | --- | --- | --- |
| 1. User makes a change | The app writes to local SQLite. | The app writes to local SQLite. Dotmim.Sync's triggers track the change. | `SaveChangesAsync()` writes the row and adds an entry to the operations queue. |
| 2. Pending write | The client SDK stores the write in a persistent upload queue, in order. | The changed rows wait in the local tables until the next sync. | The queue keeps one operation per entity, with its latest values. |
| 3. Send to the server | Your `uploadData()` function sends each change to your existing API endpoint. | At the next `SynchronizeAsync()`, the client sends changed rows to the sync endpoint in your API. | `PushAsync()` sends each operation to the table controller: `POST`, `PUT`, or `DELETE` on `/tables/{name}`, with `If-Match`. |
| 4. Business rules | Your existing endpoint applies them. | A server interceptor (`OnRowsChangesApplying`) applies them to the incoming rows. | An `IAccessControlProvider` or a repository hook applies them. |
| 5. Confirmation | The committed change syncs back and replaces the local version. | Dotmim.Sync applies the rows as upserts in one server transaction. | The server returns the stored entity, and the client marks the operation complete. |
| If the request fails | The client SDK retries after a delay, and uploads by itself when the connection returns. | Each HTTP request is retried twice. Then the sync fails, and nothing uploads until the app calls `SynchronizeAsync()` again. | The operation stays queued. Nothing uploads until the app calls `PushAsync()` again. |

{/* Dotmim.Sync retry: WebRemoteOrchestrator.EnsurePolicy in 1.3.0 uses SyncPolicy.WaitAndRetry(2, 500 ms * retry number), and does not retry HttpSessionLostException. Not in the docs. */}

{/* Datasync ordering: OperationsQueueManager.GetQueuedOperationsAsync has no ORDER BY in 10.2.0, and the docs warn that ParallelOperations > 1 "MAY be executed on the remote service out of order". */}

For an existing app, the main difference is where writes arrive. With PowerSync, your existing endpoint and its business rules stay the write path. With Dotmim.Sync and Datasync, writes arrive through a new path, and your existing endpoint isn't used. Each business rule then exists twice: in your endpoint and in the sync hook.

Each tool has its own detail to handle:

- **Dotmim.Sync:** Filters don't apply to uploads. Your interceptor also has to check that the user owns each uploaded row. Uploads are idempotent upserts keyed by the row's primary key, so a retried sync doesn't create a duplicate row. Dotmim.Sync detects conflicts per row and resolves them with `ServerWins` by default. See [Conflicts](https://dotmimsync.readthedocs.io/Conflict.html).
- **Datasync:** The queue doesn't push operations in the order the changes were made. A parent change and a child change can arrive as separate requests, in the wrong order. Datasync has built-in optimistic concurrency: the server checks `Version` with `If-Match`, and you can configure `ClientWinsConflictResolver`, `ServerWinsConflictResolver`, or your own `IConflictResolver`. A retried create gets a 409 from the server. Without a conflict resolver, that operation stays failed.
- **PowerSync:** Your endpoint decides how to handle conflicts, so the rule lives in your own code. With the simplest endpoint, the result is per-field last-write-wins, because each `PATCH` carries only the changed columns. A retry sends the whole transaction again, so your endpoint must be safe to repeat. See [Write Path Concepts](/handling-writes/write-path/concepts#retryable-errors) and [Handling Update Conflicts](/handling-writes/handling-update-conflicts).

## Rejected Writes and Stuck Queues

Sometimes your backend permanently refuses a write. A business rule says no, or the record changed on the server while the device was offline. Any of the three tools can get stuck if the app treats a permanent rejection as a temporary error. The difference is what each tool does by itself, and what you build to recover.

### PowerSync

Your `uploadData()` function classifies each response from your API. On a permanent rejection, it logs the error, records the reason, and calls `complete()` so the upload queue moves on. Your API returns the reason in a 2xx response body, or writes it to a table that syncs back to the client.

After the upload queue is empty and the client has synced, the client SDK replaces the local data with the synced copy. The rejected change disappears from the device with no extra code. See [How Changes Are Rolled Back](/handling-writes/write-path/concepts#how-changes-are-rolled-back).

If `uploadData()` throws on a permanent rejection instead, the transaction is **blocked**. Later writes from that device can't upload, and the sync status shows an `uploadError` on every attempt. See [Blocked Transactions](/handling-writes/write-path/concepts#blocked-transactions).

### Dotmim.Sync

Your server interceptor can reject a row in one of two ways:

- **Drop the row** from the rows that Dotmim.Sync applies. The sync reports success, and no reason reaches the device. The server's version of other changed rows syncs down. The device's rejected row stays in the local database, because the server never stored it and nothing tells the client to remove it.
- **Throw an exception.** The reason reaches the client in an `HttpSyncWebException`. The server rolls back the whole sync, and every later sync fails in both directions until the server accepts the row. The device stops receiving updates.

To recover without stopping sync, drop rejected rows and tell the device separately:

1. In the interceptor, drop each rejected row.
2. Record each rejection, with the user, the row ID, and the reason, in a server table. Filter that table to its user and sync it down.
3. After each sync, the app shows the latest rejection to the user.
4. When there are new rejections, the app runs a sync with `SyncType.ReinitializeWithUpload`. This sync uploads pending changes and then downloads all rows again, which removes the rejected local rows.

{/* Dotmim.Sync: dropping rows is the documented use of OnRowsChangesApplying (https://dotmimsync.readthedocs.io/Interceptors.html, "Intercepting rows"). SyncType.ReinitializeWithUpload is documented under SyncOperation on the same page. The hands-on build confirmed that ReinitializeWithUpload removes rows that the server never stored. No documented 1.3.0 API deletes local rows without tracking the delete, so the spec's "delete the rejected local rows without tracking them" option is left out. */}

For errors that the database raises while it applies a row, such as a constraint violation, Dotmim.Sync's default is also to stop and roll back the sync. Its `ErrorResolutionPolicy` option can skip the failed row or retry it on the next sync instead. See [Errors](https://dotmimsync.readthedocs.io/Errors.html).

### Datasync

When the server rejects a pushed operation with any non-success status, `PushAsync()` returns a `PushResult` with `IsSuccessful = false`. `PushResult.FailedRequests` holds the status and the response body. The operation stays in `DatasyncOperationsQueue` with `State = Failed`.

Every later `PushAsync()` sends the operation again and gets the same rejection. The local change stays in place, because the library doesn't keep a copy of the previous value.

{/* No previous value: https://github.com/CommunityToolkit/Datasync/discussions/456 (undoing a local change isn't supported; discard and pull again). */}

`PullAsync()` refuses to pull any entity type that still has a queued operation, including a failed one. It throws:

```text
DatasyncException: There are still pending operations in queue for table '<Entity>'.
```

As a result, one rejected write stops the device from receiving any server changes for that table. This check is deliberate. See [`OfflineDbContext.PullAsync`](https://github.com/CommunityToolkit/Datasync/blob/10.2.0/src/CommunityToolkit.Datasync.Client/Offline/OfflineDbContext.cs) in the Datasync source.

A rejection can happen after the device was offline, if the record changed on the server in the meantime. It can also happen online, when two devices update the same record.

Datasync's conflict resolvers run only for 409 and 412 version conflicts. They don't handle other rejections.

{/* Datasync: ServiceResponse.IsConflictStatusCode is "StatusCode is 409 or 412", and OperationsQueueManager.PushOperationAsync calls the resolver only while that is true (10.2.0). */}

To recover, handle each permanent rejection in the app. These steps are based on the Datasync docs and the maintainer's guidance in [issue #248](https://github.com/CommunityToolkit/Datasync/issues/248):

1. On the server, return a consistent status and a response body with the reason for each permanent rejection. Then the app can tell rejections apart from version conflicts and temporary errors.
2. After every `PushAsync()`, check `FailedRequests`. Show the reason for each permanent rejection to the user.
3. Remove that operation from `DatasyncOperationsQueue`.
4. Undo the local change. Delete a row that the device added, or restore the previous value. Save with `SaveChangesAsync(acceptAllChangesOnSuccess: true, addToQueue: false)` so that the fix isn't queued.
5. Delete the delta token for that entity type from `DatasyncDeltaTokens`, and pull again to get the server's current state.

These steps follow the docs' [Re-synchronizing All Data](https://communitytoolkit.github.io/Datasync/in-depth/client/#re-synchronizing-all-data) recipe, narrowed to the rejected operation. The recipe as written removes **all** pending operations for the table, which also discards the user's other unsynced changes. The Datasync docs also say to treat `DatasyncOperationsQueue` as read-only except in that recipe, but this recovery requires you to change it.

{/* Related, not for the page: https://github.com/CommunityToolkit/Datasync/issues/578 (a timed-out push left its operation queued, so the next PullAsync threw the same error) was fixed in 10.2.0. */}

## Getting Changes to the Device

The PowerSync Service streams changes to connected clients, and the app doesn't need to do anything. This includes writes made directly with SQL, which CDC captures. Latency depends on two polling intervals: the CDC capture job scans the transaction log every 5 seconds by default (1 second is recommended), and the Service polls the change tables every second by default. On Azure SQL Database, the capture job interval is fixed at 20 seconds. See [Latency](/configuration/source-db/setup#latency) and [Replication Lag](/maintenance-ops/replication-lag). Watch queries then update the UI.

Dotmim.Sync and Datasync don't push changes to the device. A sync reads SQL Server directly, so it returns current data with no replication delay. The device sees server changes only when the app syncs, for example at startup, on pull-to-refresh, or when a page opens. Datasync's [real-time tutorial](https://communitytoolkit.github.io/Datasync/tutorial/server/part-5/) sends SignalR messages from `PostCommitHookAsync`. That hook runs only for writes through the table controllers, not for writes made directly with SQL.

To get changes to devices without user action, you build:

- A push channel, such as a SignalR hub, and the infrastructure to scale it.
- Change detection on SQL Server that feeds the push channel, so writes made directly with SQL are included.
- Code in the app that syncs when a message arrives.
- A retry loop in the app, so that queued writes upload when the connection returns.

## Offline Support

All three tools support offline reads and writes, and keep pending writes across app restarts. They differ in what happens when the connection returns.

The PowerSync client SDK reconnects and uploads queued writes by itself. Its sync status reports whether the client is connected, and whether uploads or downloads are in progress or failing.

Dotmim.Sync and Datasync sync only when the app calls them. If a sync fails, it doesn't run again until the app calls it again. Neither reports a connection state, so the app infers that it is offline from the exception of the last sync. To show pending changes, a Dotmim.Sync app calls `GetEstimatedChangesCountAsync()`, and a Datasync app counts the operations in `DatasyncOperationsQueue`.

## Auth and Per-User Data

PowerSync clients connect with a JWT. [Sync Streams](/sync/streams/overview) use claims from the token, such as `auth.user_id()`, to choose the rows each client receives. When a row leaves a user's streams, for example because the user loses access, the client SDK removes it from the device. Your backend authorizes writes when `uploadData()` sends them. If your API already issues RS256 tokens and publishes a JWKS, the PowerSync Service can verify the same tokens. See [Authentication](/configuration/auth/overview).

Dotmim.Sync's sync endpoint is a normal controller in your API, protected with `[Authorize]`. See [Web Security](https://dotmimsync.readthedocs.io/WebSecurity.html). Per-user rows come from setup [filters](https://dotmimsync.readthedocs.io/Filters.html) with parameters, such as a user ID.

<Warning>
  The client sends Dotmim.Sync's filter parameters. Set them on the server from the token in an interceptor, such as `OnHttpGettingRequest`, and always overwrite the value that the client sent. Otherwise, a client can request another user's rows by sending that user's ID.
</Warning>

{/* Dotmim.Sync's "Hook Bearer token" example (https://dotmimsync.readthedocs.io/Interceptors.html) adds the parameter only when the client did not send one. */}

Filters don't apply to uploads, so your interceptor also checks that the user owns each uploaded row.

Datasync's table controllers use `[Authorize]`. `IAccessControlProvider.GetDataView()` limits which rows a user can read. `IsAuthorizedAsync()` and `PreCommitHookAsync()` control writes. See [Configure Access Permissions](https://communitytoolkit.github.io/Datasync/in-depth/server/#configure-access-permissions). Datasync has no built-in way to limit a user to changing certain columns.

On the client, Datasync's [`GenericAuthenticationProvider`](https://communitytoolkit.github.io/Datasync/in-depth/client/auth/) gets a new token only when the cached one is near expiry. A 401 response doesn't trigger a new token. If you rotate your signing key, each sync fails until the cached token nears expiry or the app calls `LoginAsync()`.

{/* GenericAuthenticationProvider (10.2.0) refreshes when now >= ExpiresOn - RefreshBufferTimeSpan (default 2 minutes) and has no 401 handling in SendAsync. */}

## Schema Changes

Adding a nullable column to a synced table takes different steps in each tool.

With PowerSync, you run `ALTER TABLE`, add a new CDC capture instance for the table, and redeploy your Sync Config. The redeploy reprocesses the data, and the previous deployment serves clients until the new one is active. Installed apps keep working, because the client-side schema is a view over schemaless data. To use the column, the app adds it to its client-side schema. See [SQL Server Specifics](/maintenance-ops/implementing-schema-changes#sql-server-specifics).

With Dotmim.Sync, you re-provision the server scope in code. After that, apps that haven't upgraded can still download changes, but can't upload them. The [Provision](https://dotmimsync.readthedocs.io/Provision.html) docs say that each client must migrate its local schema and re-provision too. An app release must therefore reach devices before you change the server. Alternatively, you can use a new scope for each schema version.

With Datasync, the server side takes three steps: `ALTER TABLE`, add the property, and redeploy. On the device, `EnsureCreated()`, which the Datasync samples use, doesn't change an existing database, and the Datasync docs have no guidance on client migrations. An upgraded app fails with `no such column` errors until it uses EF Core migrations. Rows that the device pulled before the change get the new column only when they change again on the server.
