The PowerSync JavaScript Web SDK runs SQLite in the browser and keeps it in sync with your backend database. Your UI reads and writes local data directly, so interactions feel instant because they do not wait on network round trips. Watch queries emit new results as local or synced data changes, keeping the UI current without polling.

With Sync Streams, you define the subset of backend data each client receives rather than replicating the entire database into every browser. This partial sync reduces data transfer and local storage use by keeping unrelated data out of the client database. Reading from a reactive local database also reduces the need for per-screen read APIs, cache invalidation, and client-side state plumbing. Synced data remains available even when connectivity is interrupted, enabling offline-first PWAs.

## Getting Started

**Prerequisites:** Before you start, connect your source database to the PowerSync Service and deploy Sync Streams. These are steps 1-4 in the [Setup Guide](/intro/setup-guide).

### 1. Define the Client-Side Schema

<SdkClientSideSchema />

<GenerateSchemaAutomatically />

The available column types are `text`, `integer`, and `real`. These should match the values produced by your Sync Streams. If a value does not match, it is cast automatically. For details on how source database types map to SQLite types, see [Types](/sync/types).

**Example:**

```typescript
// AppSchema.ts
import { column, Schema, Table } from '@powersync/web';

const lists = new Table({
  created_at: column.text,
  name: column.text,
  owner_id: column.text
});

const todos = new Table(
  {
    list_id: column.text,
    created_at: column.text,
    completed_at: column.text,
    description: column.text,
    created_by: column.text,
    completed_by: column.text,
    completed: column.integer
  },
  { indexes: { list: ['list_id'] } }
);

export const AppSchema = new Schema({
  todos,
  lists
});

// For types
export type Database = (typeof AppSchema)['types'];
export type TodoRecord = Database['todos'];
// OR:
// export type Todo = RowType<typeof todos>;
export type ListRecord = Database['lists'];
```

<Note>
  You do not need to declare an `id` column. PowerSync creates it automatically.
</Note>

### 2. Instantiate the PowerSync Database

Next, instantiate the PowerSync database. PowerSync streams changes from your backend source database into the client-side SQLite database, based on your Sync Streams. Your app reads from and writes to this local database whether the user is online or offline.

**Example:**

```js
import { PowerSyncDatabase } from '@powersync/web';
import { Connector } from './Connector';
import { AppSchema } from './AppSchema';

export const db = new PowerSyncDatabase({
  // The schema you defined in the previous step
  schema: AppSchema,
  database: {
    // Filename for the SQLite database — it's important to only instantiate one instance per file.
    dbFilename: 'powersync.db',
    // Use a suitable OPFS storage (recommended). The default is IndexedDB for backwards compatibility.
    vfs: 'auto',
    // Optional. Directory where the database file is located.
    // dbLocation: 'path/to/directory'
  }
});
```

After you instantiate the PowerSync database, call the [connect()](https://powersync-ja.github.io/powersync-js/common/interfaces/CommonPowerSyncDatabase#connect) method to sync data with your backend.

<LocalOnly />

```js
export const setupPowerSync = async () => {
  // Uses the backend connector that you create in the next step
  const connector = new Connector();
  db.connect(connector);
};
```

### 3. Integrate with Your Backend

The backend connector connects the PowerSync client SDK to your application backend. The SDK uses it to:

1. Get an auth token to connect to the PowerSync instance.
2. Upload client-side writes to your backend API. The SDK places every write to the SQLite database in an upload queue and uploads the queue to your backend when the user is connected. Your backend then applies the changes to the source database.

The connector must implement two methods:

1. [PowerSyncBackendConnector.fetchCredentials](https://github.com/powersync-ja/powersync-js/blob/ed5bb49b5a1dc579050304fab847feb8d09b45c7/packages/common/src/client/connection/PowerSyncBackendConnector.ts#L16) - The SDK calls this method to get authentication credentials. It caches the credentials and calls the method again only when needed, for example on the first connection or when the token is near expiry. See [When `fetchCredentials()` is Called](/configuration/app-backend/client-side-integration#when-fetchcredentials-is-called) for details and [Authentication Setup](/configuration/auth/overview) for how to generate credentials.
2. [PowerSyncBackendConnector.uploadData](https://github.com/powersync-ja/powersync-js/blob/ed5bb49b5a1dc579050304fab847feb8d09b45c7/packages/common/src/client/connection/PowerSyncBackendConnector.ts#L24) - The SDK calls this method whenever it has client-side writes to upload to your backend API. Implement how those writes are processed and uploaded. See [When `uploadData()` is Called](/configuration/app-backend/client-side-integration#when-uploaddata-is-called) for triggers, throttling, and retry behavior, and [Writing Client Changes](/handling-writes/writing-client-changes) for the app backend implementation.

**Example:**

```js
import { UpdateType } from '@powersync/web';

export class Connector {
  async fetchCredentials() {
    // Implement fetchCredentials to obtain a JWT from your authentication service. 
    // See https://docs.powersync.com/configuration/auth/overview
    return {
        endpoint: '[Your PowerSync instance URL or self-hosted endpoint]',
        // Use a development token (see Authentication Setup https://docs.powersync.com/configuration/auth/development-tokens) to get up and running quickly
        token: 'An authentication token'
    };
  }

  async uploadData(database) {
    // Implement uploadData to send local changes to your backend service.
    // You can omit this method if you only want to sync data from the database to the client

    // See example implementation here: https://docs.powersync.com/client-sdks/usage-examples#send-changes-in-local-data-to-your-backend-service
  }
}
```

## Using PowerSync: CRUD Functions

Once the PowerSync database is connected and your streams have synced, the data is in the local SQLite database.

The most commonly used CRUD functions to interact with your SQLite data are:

- [PowerSyncDatabase.get](/client-sdks/reference/javascript-web#fetching-a-single-item) - get (`SELECT`) a single row from a table.
- [PowerSyncDatabase.getAll](/client-sdks/reference/javascript-web#querying-items-powersync-getall) - get (`SELECT`) a set of rows from a table.
- [PowerSyncDatabase.watch](/client-sdks/reference/javascript-web#watching-queries-powersync-watch) - execute a read query every time a dependent table changes.
- [PowerSyncDatabase.execute](/client-sdks/reference/javascript-web#mutations-powersync-execute-powersync-writetransaction) - execute a write (`INSERT`/`UPDATE`/`DELETE`) query.

### Fetching a Single Item

The [get](https://powersync-ja.github.io/powersync-js/common/interfaces/CommonPowerSyncDatabase#get) method executes a read-only (SELECT) query and returns a single result. It throws an exception if no result is found. Use [getOptional](https://powersync-ja.github.io/powersync-js/common/interfaces/CommonPowerSyncDatabase#getoptional) to return a single optional result (returns `null` if no result is found).

```js
// Find a list item by ID
export const findList = async (id) => {
  const result = await db.get('SELECT * FROM lists WHERE id = ?', [id]);
  return result;
}
```

### Querying Items (PowerSync.getAll)

The [getAll](https://powersync-ja.github.io/powersync-js/common/interfaces/CommonPowerSyncDatabase#getall) method returns a set of rows from a table.

```js
// Get all lists
export const getLists = async () => {
  const results = await db.getAll('SELECT * FROM lists');
  return results;
}
```

### Watching Queries (PowerSync.watch)

The [watch](https://powersync-ja.github.io/powersync-js/common/interfaces/CommonPowerSyncDatabase#watch) method executes a read query whenever a change to a dependent table is made.

### Mutations (PowerSync.execute, PowerSync.writeTransaction)

The [execute](https://powersync-ja.github.io/powersync-js/common/interfaces/CommonPowerSyncDatabase#execute) method can be used for executing single SQLite write statements.

```js
// Delete a list by ID
export const deleteList = async (id) => {
  await db.execute('DELETE FROM lists WHERE id = ?', [id]);
};

// OR: delete the list and its todos in one transaction
export const deleteListWithTodos = async (id) => {
  await db.writeTransaction(async (tx) => {
    await tx.execute('DELETE FROM todos WHERE list_id = ?', [id]);
    await tx.execute('DELETE FROM lists WHERE id = ?', [id]);
  });
};
```

## Developer Notes

### Connection Methods

This SDK supports two methods for streaming sync commands:

1. **HTTP Streaming (Default)**
   - This is the default and recommended connection method.
2. **WebSocket**
   - This implementation uses RSocket over WebSocket connections.
   - To customize window sizes for flow control and back-pressure, set `fetchStrategy` to `Buffered` (default) or `Sequential`.
   - On the web, there is no compelling reason to use WebSockets over HTTP response streams.

By default, the `PowerSyncDatabase.connect()` method uses HTTP streaming. You can optionally specify the `connectionMethod` to override this:

```js
// HTTP Streaming (default)
powerSync.connect(connector);

// WebSocket
powerSync.connect(connector, { connectionMethod: SyncStreamConnectionMethod.WEB_SOCKET });
```

### SQLite Virtual File Systems

The SDK stores its local SQLite database through a virtual file system (VFS), the layer SQLite uses to read and write files. The VFS determines whether data persists, how tabs share data, and whether reads can run concurrently.

For new apps that need to support a wide range of browsers, use [`vfs: 'auto'`](#automatic-vfs-selection-recommended). It selects [`SimpleOpfsVFS`](#simpleopfsvfs), which supports multiple tabs across major browsers, when the Origin Private File System (OPFS) is available. If OPFS is unavailable, or you disable web workers, it uses an in-memory database that does not persist data. If your app primarily targets Safari, use [`OPFSCoopSyncVFS`](#opfscoopsyncvfs) for now.

If you omit `vfs`, the SDK uses [`IDBBatchAtomicVFS`](#idbbatchatomicvfs-default) and stores data in IndexedDB. This remains the default for backward compatibility.

#### Automatic VFS Selection

The `'auto'` option is available in `@powersync/web` version 2.7.0 and later. Use it for new apps that need broad browser support. It selects [`SimpleOpfsVFS`](#simpleopfsvfs) when OPFS is available and web workers are enabled. If your app primarily targets Safari, use [`OPFSCoopSyncVFS`](#opfscoopsyncvfs) for now.

Switching from `SimpleOpfsVFS` to `'auto'` reuses the database if `'auto'` selects that VFS and you keep the file name and storage location unchanged. The SDK does not migrate data from other VFS implementations.

Example configuration:

```js
import { PowerSyncDatabase } from '@powersync/web';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'exampleVFS.db',
    vfs: 'auto'
  }
});
```

#### SimpleOpfsVFS

`WASQLiteVFS.SimpleOpfsVFS` is a simplified version of `OPFSCoopSyncVFS`. Both store data in OPFS and support multiple tabs across major browsers. `SimpleOpfsVFS` is designed specifically for a single PowerSync database instead of supporting every SQLite file system feature. The SDK selects one of three strategies based on the browser's capabilities:

1. **Shared workers (Firefox, Safari 27.3+):** Synchronous OPFS access is available only in dedicated workers. On these browsers, a shared worker can open a dedicated worker, allowing tabs to share one database connection.
2. **Concurrent file handles (Chromium-based browsers):** Multiple tabs open the same database files and use navigator locks to prevent concurrent writes.
3. **Open coordination (fallback, including older Safari versions):** A tab keeps the database files open until another tab requests access. Once the database is idle, it closes the files so the other tab can proceed.

`SimpleOpfsVFS` can be more susceptible to the [known Safari issue](#opfscoopsyncvfs). If your app primarily targets Safari, use `OPFSCoopSyncVFS` for now.

This VFS doesn't support `ATTACH` for additional databases, and SQLite temporary data, such as materialized CTEs, always stays in memory.

To select this VFS explicitly, import `WASQLiteVFS` and set `database.vfs`:

```js
import { PowerSyncDatabase, WASQLiteVFS } from '@powersync/web';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'exampleVFS.db',
    vfs: WASQLiteVFS.SimpleOpfsVFS
  }
});
```

#### IDBBatchAtomicVFS (Default)

`WASQLiteVFS.IDBBatchAtomicVFS` stores data in IndexedDB. It is the default when you omit the `vfs` option. The SDK keeps this default for backward compatibility, so existing apps continue to open their IndexedDB databases without changing their configuration.

Use this VFS if your app cannot use database workers and requires persistence. Unlike OPFS, IndexedDB is available without a database worker. See [PowerSyncDatabase Flags](#available-flags) for the related configuration.

To select this VFS explicitly:

```js
import { PowerSyncDatabase, WASQLiteVFS } from '@powersync/web';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'exampleVFS.db',
    vfs: WASQLiteVFS.IDBBatchAtomicVFS
  }
});
```

#### OPFSCoopSyncVFS

`WASQLiteVFS.OPFSCoopSyncVFS` stores data in OPFS and supports multiple tabs across major browsers, including Safari on iOS.

Use this VFS if your app primarily targets Safari because `SimpleOpfsVFS` can be more susceptible to a known Safari issue. For broad browser support, use [`vfs: 'auto'`](#automatic-vfs-selection-recommended).

To select this VFS explicitly:

```js
import { PowerSyncDatabase, WASQLiteVFS } from '@powersync/web';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'exampleVFS.db',
    vfs: WASQLiteVFS.OPFSCoopSyncVFS
  }
});
```

#### OPFSWriteAheadVFS

`WASQLiteVFS.OPFSWriteAheadVFS` stores data in OPFS and uses its own write-ahead log so reads can run while a write is in progress. The SDK opens additional read-only connections in separate workers, which lets multiple queries run at the same time. Use it if you need concurrent reads and only target Chromium-based browsers, such as Chrome or Edge.

The `additionalReaders` option sets how many read-only connections the SDK opens in addition to the main connection. It defaults to `1`. Increase it if your app often runs many read queries at once. Each additional reader uses more memory.

This example opens two additional readers. When the main connection is idle, it can serve a third read query:

```js
import { PowerSyncDatabase, WASQLiteVFS } from '@powersync/web';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'exampleVFS.db',
    vfs: WASQLiteVFS.OPFSWriteAheadVFS,
    additionalReaders: 2
  }
});
```

#### AccessHandlePoolVFS

`WASQLiteVFS.AccessHandlePoolVFS` stores data in OPFS but does not support sharing the database across tabs. It is retained for backward compatibility and is not recommended for new apps.

#### InMemoryVfs

`WASQLiteVFS.InMemoryVfs` stores database files in memory, avoiding the overhead of reading and writing them through OPFS or IndexedDB. Use it for development or online-only apps with small datasets when you don't need persistence. It is available in `@powersync/web` version 2.0.0 and later.

Starting with an empty database can help you reproduce issues from a clean state during development. If tabs share an in-memory database through a shared worker, closing the last tab using it clears the database. Otherwise, each tab has its own database, which is cleared when that tab closes or reloads.

Any mutations that haven't uploaded are lost when the database is cleared. A new in-memory database must download its synced data again after you connect, so consider how much data your app needs at startup.

<Warning>
  In production, consider watching `SELECT * FROM ps_crud LIMIT 1` to detect pending mutations and show users when the upload queue is not empty. A [`beforeunload` listener](https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event#usage_notes) can request confirmation before closing a tab with pending mutations, but it is not reliable on all platforms.
</Warning>

If you disable `enableMultiTabs`, only one database with a given name syncs at a time. Give each tab a unique database file name to let every tab sync independently:

```js
import { PowerSyncDatabase, WASQLiteVFS } from '@powersync/web';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: `memory-${crypto.randomUUID()}.db`,
    vfs: WASQLiteVFS.InMemoryVfs,
    enableMultiTabs: false
  }
});
```

### Multi-Threaded In-Memory SQLite Connection Pool

Since version 2.2.0, the `@powersync/web` package provides an experimental, per-tab in-memory SQLite connection pool for highly concurrent query workloads. It uses a design inspired from `OPFSWriteAheadVFS`, but relies on `SharedArrayBuffer` to coordinate an in-memory database instead of persisting to OPFS. It is available under a separate import and is thus configured via the `opened` option on `PowerSyncDatabase` instead of `database.vfs`.

<Note>
  This setup is experimental and might change in the future.
</Note>

The pool creates `numWorkers` SQLite connections in dedicated web workers. One worker is the designated writer, while the remaining workers are used as additional readers. The writer can also serve reads while it is idle.

Read-only transactions can run in parallel, including while the writer is writing. This helps when queries overlap, but it does not make an individual query faster. Additional workers increase initialization time and memory use.

Each pool instance is independent and belongs to one tab. Its data is not persisted or shared across tabs, and the application cannot assign it a database filename. Opening or refreshing a tab creates a fresh database that must be resynced. Any local writes that have not been uploaded are lost when the tab closes.

This option requires cross-origin isolation and browser support for growable `SharedArrayBuffer`. The connection pool cannot be created without them.

This connection pool is primarily relevant when all of the following apply:

1. You need to run read queries concurrently.
2. Your dataset is small enough to download again whenever a tab opens.
3. You don't need persistence.
4. You can enable [cross-origin isolation](https://web.dev/articles/cross-origin-isolation-guide) by using the appropriate headers.
5. You don't need multiple tabs to share offline state.

Import the pool from `@powersync/web/extra/shared-memory-pool` and pass it through the `opened` option:

```js
import { InMemoryWriteAheadLogPool } from '@powersync/web/extra/shared-memory-pool';
import { PowerSyncDatabase } from '@powersync/web';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  opened: new InMemoryWriteAheadLogPool({
    numWorkers: 3 // Uses one writer, two additional workers for reads.
  }),
});
```

### Managing OPFS Storage

The following utility functions can help you manage OPFS storage programmatically:

```js
// Clear all OPFS storage
async function purgeVFS() {
  await powerSync.disconnect();
  await powerSync.close();

  const root = await navigator.storage.getDirectory();
  await new Promise(resolve => setTimeout(resolve, 1)); // Allow .db-wal to become deletable

  for await (const [name, entry] of root.entries()) {
    try {
      if (entry.kind === 'file') {
        await root.removeEntry(name);
      } else if (entry.kind === 'directory') {
        await root.removeEntry(name, { recursive: true });
      }
    } catch (err) {
      console.error(`Failed to delete ${entry.kind}: ${name}`, err);
    }
  }
}

// List OPFS entries
async function listVfsEntries() {
  const root = await navigator.storage.getDirectory();
  for await (const [name, entry] of root.entries()) {
    console.log(`${entry.kind}: ${name}`);
  }
}
```

### Multiple Tab Support

Think of PowerSync's multi-tab behavior as two separate layers:

1. **Local database access:** The VFS determines whether tabs can access the same local database and how they coordinate that access.
2. **Sync connection:** The `enableMultiTabs` option controls whether tabs share one sync connection through a shared worker. Without a shared worker, only one tab syncs at a time for a given database name.

PowerSync supports multi-tab database access on most desktop browsers. When shared-worker mode is enabled, the SDK creates a shared worker named `shared-powersync-[dbFileName]` to manage one sync connection for the tabs.

The shared sync worker connects to the PowerSync Service and applies downloaded changes on behalf of all tabs. It calls the `fetchCredentials` and `uploadData` methods from the connector provided by the most recently registered tab that is still open. When that tab closes, the worker uses the connector from another registered tab.

<Warning>
  - The SDK disables shared-worker sync by default on Android, iOS, and Safari. See [Behavior Without Shared Workers](#behavior-without-shared-workers).
  - If your app primarily targets Safari, use [`OPFSCoopSyncVFS`](#opfscoopsyncvfs) for multi-tab database access. It has a [known Safari issue](https://github.com/powersync-ja/powersync-js/issues/808), but `SimpleOpfsVFS` can be more susceptible to it.
</Warning>

#### Behavior Without Shared Workers

PowerSync does not use shared-worker mode when the browser does not support it, the SDK disables it by default for the platform, or you set `enableMultiTabs: false`. To disable it explicitly:

```js
export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'my_app_db.sqlite',
    enableMultiTabs: false
  },
});
```

Without shared-worker mode, each tab manages its own sync implementation, but only one tab syncs at a time for a given database name. Whether tabs access the same local data still depends on the VFS. With `InMemoryVfs`, each tab has its own database.

The SDK uses broadcast channels to share watched-query updates between tabs. Since version 2.1.0, it also shares sync status and Sync Stream subscriptions this way. This coordination is less reliable than using a shared worker, so updates may not reach every tab.

### Using PowerSyncDatabase Flags

The `PowerSyncDatabase` constructor accepts the following flags. Use them to enable or disable specific features.

#### Configuring Options

Set database options inside `database`. Set `broadcastLogs` at the top level of the `PowerSyncDatabase` constructor options:

```javascript
import { PowerSyncDatabase } from '@powersync/web';
import { AppSchema } from '@/library/powersync/AppSchema';

export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'example.db',
    enableMultiTabs: true,
  },
  broadcastLogs: true,
});
```

#### Available Flags

<ParamField path="database.enableMultiTabs">
  default: `true` when shared workers are available, except on Android, iOS, and Safari

  Controls whether tabs share one sync connection through a shared worker. Depending on the VFS, they may also share a database connection. Setting this option to `false` does not prevent a supported VFS from providing multi-tab database access. Requires browser support for shared workers.
</ParamField>

<ParamField path="broadcastLogs">
  default: `true`

  Enables the broadcasting of logs for debugging purposes. This flag helps monitor shared worker logs in a multi-tab environment.
</ParamField>

<ParamField path="database.disableSSRWarning">
  default: `false`

  Disables warnings when running in SSR (Server-Side Rendering) mode.
</ParamField>

<ParamField path="database.ssrMode">
  default: `false` in the browser; `true` when `window` is not defined

  Enables SSR mode. In this mode, only empty query results will be returned, and syncing with the backend is disabled.
</ParamField>

<ParamField path="database.useWebWorker">
  default: `true`

  Runs database operations in web workers. If you disable this option, also set `enableMultiTabs: false`.
</ParamField>

#### Flag Behavior

**Example 1: Disable Shared-Worker Mode**

To give each tab its own sync implementation instead of using a shared sync worker:

```javascript
export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'my_app_db.sqlite',
    enableMultiTabs: false,
  },
});
```

When disabled, each tab manages its own sync implementation, but only one tab syncs at a time for a given database name. See [Behavior Without Shared Workers](#behavior-without-shared-workers).

**Example 2: Verbose Debugging with Broadcast Logs**

To enable detailed logging for debugging:

```javascript
export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'my_app_db.sqlite',
    databaseWorkerLogLevel: LogLevels.debug,
  },
  sync: {
    logLevel: LogLevels.debug,
  },
  logger: createConsoleLogger({ minLevel: LogLevels.debug }),
});
```

Logs include details of database and sync operations.

#### Recommendations

1. Choose a VFS that supports multi-tab database access if tabs must use the same local data.
2. Leave `enableMultiTabs` at its default to use shared-worker mode where the SDK enables it. Setting it to `false` disables shared workers, not all multi-tab database access.
3. Set `broadcastLogs` to `true` during development to troubleshoot and monitor database and sync operations.
