This route uses the [reference write implementation](/handling-writes/write-path/reference-write-implementation). You deploy its write endpoint as a Supabase Edge Function, and your app sends writes to the function with the reference uploader. Compared with the [PostgREST route](/handling-writes/write-path/supabase-postgrest), you deploy and maintain one function, and in return each transaction is applied in one database transaction.

The function runs each write as the signed-in user. Inside each transaction, it switches to the `authenticated` role and sets the user's token claims. Policies that use `auth.uid()` therefore work the same way as for requests from the Supabase client SDKs.

## Before You Start

- PowerSync connected to your Supabase project and configured for [Supabase Auth](/configuration/auth/supabase-auth). See the [Supabase guide](/integrations/supabase/guide).
- Your Supabase project signs tokens with asymmetric JWT signing keys, the default for new projects. Projects that use the legacy JWT secret must [migrate](/configuration/auth/supabase-auth#migrating-from-legacy-to-new-jwt-signing-keys) first.
- Each table that your app writes to has an `id` primary key or unique column that holds the client's row ID.
- An app that signs users in with Supabase Auth.
- The [Supabase CLI](https://supabase.com/docs/guides/local-development/cli/getting-started).

## Set Up

<Steps>
  <Step title="Add Grants and RLS Policies">
    <SupabaseGrantsAndRls />
  </Step>
  <Step title="Deploy the Function">
    Clone [powersync-reference-write-implementation](https://github.com/powersync-ja/powersync-reference-write-implementation/tree/main). From its `backend` folder, link your project and deploy the function:

    ```bash
    supabase link --project-ref <project-ref>
    supabase functions deploy powersync-write
    ```

    If Docker isn't running, add `--use-api` to the deploy command.

    The function connects to your project's database directly. Each function worker keeps up to three connections, and they all count against your database's connection limit. If many workers run at once, set the function to use the transaction pooler. To configure it, copy the pooler connection string from **Connect** > **Transaction pooler** in the Supabase dashboard. URL-encode any special characters in the password and add `sslmode=verify-full`:

    ```bash
    supabase secrets set POWERSYNC_DATABASE_URL='postgresql://postgres.<project-ref>:<password>@<pooler-host>:6543/postgres?sslmode=verify-full'
    ```

    <Warning>
      From this repository, run only `supabase functions deploy powersync-write` and `supabase secrets set` against your project. Other commands, such as `supabase config push`, can apply the repository's local development config to your project.
    </Warning>

    To deploy from your own repository instead, see the repository's [Supabase Edge Function guide](https://github.com/powersync-ja/powersync-reference-write-implementation/blob/main/backend/supabase/README.md#deploy-to-your-project).
  </Step>
  <Step title="Check the Deployment">
    ```bash
    curl -i -X POST https://<project-ref>.supabase.co/functions/v1/powersync-write/api/data
    ```

    A request without a token returns `401`.
  </Step>
  <Step title="Connect Your App">
    <span id="connect-your-app" />

    Your app needs two files from [Client Connection Examples](/configuration/app-backend/client-connection-examples):

    - The Supabase authenticator from the [Supabase examples](/configuration/app-backend/client-connection-examples#supabase). It gives the SDK the access token of the current Supabase session.
    - The reference uploader from the [Custom Backend examples](/configuration/app-backend/client-connection-examples#custom-backend). It sends writes to the Edge Function with the same token.

    In your copy of the uploader, set the write endpoint URL to `https://<project-ref>.supabase.co/functions/v1/powersync-write`. Then connect with the Supabase authenticator and the uploader, and pass the Supabase authenticator to the uploader in place of `MyAuthenticator`. Your PowerSync instance URL doesn't change.

    The Supabase authenticator caches the token. The SDK clears the cache before the token expires, and the uploader clears it when the Edge Function rejects the token, so the next request uses the current session's token. In Kotlin, `SupabaseAuthenticator` from the Supabase integration doesn't cache: it reads the current session's token on each request.

    For example, in TypeScript:

    ```typescript
    // SupabaseAuthenticator and MyMutationUploader are the two files that you copied.
    const authenticator = new SupabaseAuthenticator();
    await db.connect({
      powerSyncEndpoint: authenticator.config.powersyncUrl,
      authenticator,
      upload: new MyMutationUploader({ authenticator }).upload
    });
    ```

    The function accepts only a signed-in user's access token. It rejects API keys, anon tokens, and service-role tokens.
  </Step>
</Steps>

## How Failures Are Handled

| Failure | Outcome |
| --- | --- |
| An RLS policy or missing grant denies a write | [Blocked transaction](/handling-writes/write-path/concepts#blocked-transactions). The function reports the denial as a retryable error, so the uploader keeps the transaction and the SDK retries it. No write is lost, but until you fix the policy, grant, or data, it holds back every later write from that device. To change this, edit `permissionErrorsRetryable` in `rls.ts`. |
| `authorize()` in `authorizer.ts` returns `false` | [Rejected write](/handling-writes/write-path/concepts#rejected-writes). The uploader removes the transaction from the queue, and the function passes it to the dead-letter hook. To keep these transactions in the queue instead, change `requiresClientHandling` in `fatal-error-handler.ts`. |
| Constraint violation, invalid data, another permanent error, or any database error the function doesn't recognize | [Rejected write](/handling-writes/write-path/concepts#rejected-writes). The uploader removes the transaction from the queue, and the function passes it to the dead-letter hook in `fatal-error-handler.ts`, which only logs it by default, so the user's change is lost. |
| Temporary error, such as a lost connection | Retryable error. |

A policy can also hide a row from the user. A `PATCH` or `DELETE` on a hidden row succeeds without changing anything. The app's local change reverts after the next sync.

Because an RLS denial is retried, a mistake in a policy shows up as a growing upload queue and repeated `uploadError` values in the sync status. To stop one denied write from holding up the queue, add a retry limit to your copy of the uploader. When a transaction reaches the limit, drop it or store it.

## Customization

Edit these files in `backend/supabase/functions/powersync-write/`, then deploy again:

| File | Use it to |
| --- | --- |
| `mapper.ts` | Map client tables and columns to different names in Postgres. |
| `authorizer.ts` | Add checks that RLS can't express, such as rejecting a transaction based on the tables it touches. RLS still applies to every write it allows. |
| `fatal-error-handler.ts` | Choose which permanent failures become blocked transactions, and store rejected writes. The function waits for the dead-letter hook before it responds, so a slow hook delays uploads. In the app, the uploader's `onFatalTransaction()` keeps blocked transactions by default. |
| `config.ts` | Change the batch failure policy, the connection pool size, and the statement timeout. |
