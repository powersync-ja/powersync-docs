These concepts apply to every write path setup, whether you use your own API or Supabase.

## Authenticating Writes

Your write API receives requests from your users' devices, so it must authenticate each request before it applies any change.

If your auth provider issues JWTs, your write API can verify the same JWT that your app sends to PowerSync. Your backend connector's `fetchCredentials()` already returns this token, so `uploadData()` can send it in the request's `Authorization` header. To verify the token, your write API must:

1. Check the signature with your auth provider's keys, usually from its JWKS URL.
2. Check the issuer and expiry.
3. Accept the token's audience. With Auth0 and custom JWTs, the audience is your PowerSync instance URL. With Firebase Auth, it is your Firebase project ID. A write API that expects a different audience rejects the token.

The `sub` claim holds the user ID. Use it to decide which writes that user is allowed to make. See [Authentication](/configuration/auth/overview) for the audience and keys each provider uses.

## What Happens When a Write Fails

The SDK removes changes from the upload queue only when `uploadData()` marks them complete. If `uploadData()` throws an error, or returns without marking them complete, the changes stay in the queue and the SDK calls `uploadData()` again after a delay. It keeps doing this while the sync stream is connected. For details, see [Error Handling](/configuration/app-backend/client-side-integration#error-handling).

The queue is ordered, so changes that stay at the front hold back every write behind them. When a write fails, your write API and `uploadData()` decide between the following outcomes.

### Retryable Errors

A **retryable error** is a failure that is likely to succeed later without any change to the write, such as a network error, a timeout, or a database that is temporarily unavailable. `uploadData()` throws, and the SDK retries.

If `uploadData()` also throws for a write that can never succeed, such as one that violates a constraint, the SDK retries it until someone fixes the cause, and no later writes upload. This happens for any response status, 4xx or 5xx. The sync status shows an `uploadError` on every attempt.

### Rejected Writes

A **rejected write** is a write that your write API will never apply, for example because it fails validation. The write API tells `uploadData()` that it rejected the write, preferably with a 2xx response that includes the reason. `uploadData()` then marks the write complete, and the queue keeps moving.

The rejected change stays in the local database until the upload queue is empty and the client has synced. Then the local data is replaced with the state from your source database. See [How Changes Are Rolled Back](/handling-writes/handling-write-validation-errors#how-changes-are-rolled-back).

To keep a record of rejected writes, your write API can store each one in a **dead-letter queue**: a table or queue on your backend that you inspect later. See [Dead-Letter Queue](/handling-writes/handling-write-validation-errors#dead-letter-queue) for the ordering trade-off this brings.

### Blocked Transactions

A **blocked transaction** is a failed transaction that your app keeps in the upload queue on purpose until someone decides what to do with it. For example, the write API refuses a write because the user lacks a permission that an administrator can grant. `uploadData()` throws instead of marking the transaction complete, so no later writes upload.

Your app needs a way to resolve a blocked transaction, such as showing the problem to the user. When the cause is fixed, the next retry succeeds. If the write should be dropped instead, `uploadData()` marks the transaction complete, and the change is rolled back like a rejected write.
