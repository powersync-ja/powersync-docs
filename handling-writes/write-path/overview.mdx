PowerSync syncs data from your source database to your app. Your own code applies your app's writes to the source database, so your backend can run its own business logic, validation, and authorization before a change is stored.

<Frame caption="PowerSync handles the read path. The write path, drawn with dashed lines, is the part you build.">
  ![Diagram of the PowerSync architecture. The source database replicates to the PowerSync Service, which syncs to the SDK in the client app. Two dashed boxes marked with question marks, uploadData() and a write API, carry writes from the SDK back to the source database. An auth provider issues the JWTs.](/images/handling-writes/write-path-overview.png)
</Frame>

The two parts marked with a question mark are yours to build:

- `uploadData()`: a function in your app's backend connector. The SDK calls it when the upload queue has changes. It sends the changes to your write API, then marks the transaction complete. If it throws an error, the SDK retries later.
- **Write API**: a backend endpoint that receives the changes and applies them to your source database. It needs to authenticate each request. If your auth provider issues JWTs, the write API can verify the same JWT that your app sends to PowerSync. See [Authenticating Writes](/handling-writes/write-path/concepts#authenticating-writes).

## How a Write Reaches Your Source Database

In these steps, your backend API is the write API.

<WritePathSteps />

Your app sees its own change immediately after step 1, because it reads from the local database. Other users' apps see it after step 5. If your write API rejects or changes the write, the synced result replaces the local change. While the device is offline, steps 2 to 5 wait until it reconnects.
