Your existing API can serve as your write API. Your API may need small changes so that its responses tell `uploadData()` what to do with each change.

## What `uploadData()` Must Do

Your `uploadData()` function reads queued transactions from the database. Each change is a `PUT`, `PATCH`, or `DELETE` on one row of a table in your client-side schema. See [Write Operations Recorded on the Client](/handling-writes/writing-client-changes#write-operations-recorded-on-the-client).

For each transaction, `uploadData()` must:

1. Send each change to the matching endpoint of your API, authenticated the way your API expects. If your auth provider issues JWTs, this can be the token your app sends to PowerSync. See [Authenticating Writes](/handling-writes/write-path/concepts#authenticating-writes).
2. Classify the result of each call as success, a [retryable error](/handling-writes/write-path/concepts#retryable-errors), or a [rejected write](/handling-writes/write-path/concepts#rejected-writes).
3. Throw on a retryable error, such as a network error or a 5xx response. The SDK keeps the transaction and retries it later.
4. Log a rejected write and continue. If your API returns 4xx for validation errors or conflicts, treat those responses as rejected writes. Throwing on them instead turns them into a [blocked transaction](/handling-writes/write-path/concepts#blocked-transactions). A 401 from an expired token is different: refresh the token and retry.
5. Mark the transaction complete once every change in it was applied or rejected.

If your code catches an error without throwing it again and then marks the transaction complete, the change is lost without any error.

A retry sends the whole transaction again, including changes your API already applied. Make each call safe to repeat, so that a create that already exists or a delete of a missing row is not reported as a rejected write.

## What Your API Must Do

- **Apply changes before responding.** Write to the source database while the request is open, instead of queueing the work for later. After an upload, the client waits for a checkpoint that includes its changes. If a change is not in the source database yet, it disappears from the device until it syncs back. See [Consistency](/architecture/consistency).
- **Return 5xx only for temporary errors.** Use 5xx for problems that clear up, such as a database that is briefly unavailable. A 5xx for a write that can never succeed makes `uploadData()` retry it until someone fixes the cause.
- **Report rejected writes.** For validation errors and conflicts, return 2xx with the reason in the response body, or write the reason to a table that syncs back to the client, so your app can show it to the user. See [Handling Write / Validation Errors](/handling-writes/handling-write-validation-errors).

Any API style works, with one endpoint or several. One request per change is fine for typical volumes. If your app makes many writes at once, such as bulk imports, an endpoint that accepts a batch of changes needs fewer requests. See [Writing Client Changes](/handling-writes/writing-client-changes) for the options.

## Find the existing PowerSync setup

Look for, in this order:

1. **The existing connector file:** usually named something like `*Connector.ts`/`*Connector.dart`/similar, implementing the PowerSync SDK's backend connector interface and containing (or stubbing) `uploadData`. This is the file you'll be editing.
2. **The client schema:** usually `AppSchema.ts`/`schema.ts` or similar, defining `Table`s passed to `Schema(...)`. This tells you the table/column shape backing each mutation's `opData` (a `CrudEntry`), which you need to map mutations onto backend requests.
3. **The backend API surface:** an existing OpenAPI/Swagger spec, generated API client, or hand-written `fetch`/`axios`/similar wrapper calling this project's backend. Most PowerSync customers already have a working backend API and are connecting `uploadData` to it rather than building a new one. Assume that's the case here unless told otherwise.

If you can't find the backend API surface in this repo (for example, the backend lives in a separate repo, or there isn't one yet), ask me for: the relevant endpoint(s) or API docs, the auth mechanism to use, and how the API reports validation/conflict errors (status codes, error body shape).

## Known failure modes to design against

These come from recurring PowerSync support reports. Treat them as requirements:

- **Stuck upload queue.** A common `uploadData` bug: one mutation that always fails is retried forever and blocks every mutation queued behind it. Every error path below must end in one of two ways: the mutation succeeds, or it's classified and handled (retried, or discarded with an error log). No error can be silently ignored. The backend matters here too: a 5xx must mean "try again later", never "this will never work", because a "retryable" error that always fails is a stuck queue. A retry cap, in the hardening list near the end, is the client-side safety net for a backend that can't promise that.
- **`complete()` must never be called on a caught/swallowed error.** Apps have lost mutations this way: an error handler didn't throw the error again, so `complete()` ran as if the mutation had succeeded. Only call `complete()` after a real success, or after you've decided to discard or dead-letter a mutation.
- **Classify errors explicitly, not only as success or failure.** Many existing `uploadData` implementations only distinguish "it worked" from "it didn't", which is what leads to stuck queues and lost data. Every backend call must resolve to one of: `success`, `retryable_error` (network error, timeout, 5xx: try again), or `fatal_error` (validation, conflict, 4xx that isn't going to succeed on retry).
- **Retries re-send mutations that were already applied.** A `retryable_error` partway through a transaction leaves the whole transaction in the queue, so the next attempt sends the earlier mutations again. Each backend call must be safe to repeat: a create that already exists, or a delete of a row that is already gone, must not turn into a `fatal_error` that discards later work. Ask me how the backend handles a repeated create if you can't tell.
- **Batch size does not reduce the number of requests.** `BATCH_SIZE` only sets how many transactions one `uploadData` call processes, and the SDK calls `uploadData` again until the queue is empty. The code below still sends one request per mutation. If request volume is a problem (large imports, bulk UI actions), the fix is a backend endpoint that accepts a batch of mutations; raise that with me rather than raising `BATCH_SIZE`.

## Implementation to translate, not rewrite from scratch

The code below fully specifies the control flow: batching, error classification, and completion. It's written for the common case where the backend is a set of existing per-resource REST endpoints rather than a transaction-atomic write API. If the backend can apply a whole transaction in one request, tell me before you write code. In that case, the PowerSync reference connector at https://github.com/powersync-ja/powersync-reference-write-implementation/tree/main/example-client, which uploads whole transactions, is a better starting point than the code below.

Translate this into the project's actual language/SDK (Dart, Kotlin, Swift, C#, JS/TS, or whatever this project uses), keeping the structure, comments, and error handling intact. The only part to design from scratch is `callBackendApi`. Everything else should be a close translation.

```typescript
import type { AbstractPowerSyncDatabase, CrudEntry, CrudTransaction } from '@powersync/web';

// --- Config, answered by me above ---
const BATCH_SIZE = /* transactions per uploadData call */;

// --- What every backend call must resolve to ---
type MutationOutcome =
  | { status: 'success' }
  | { status: 'retryable_error'; message?: string }
  | { status: 'fatal_error'; errorCode?: string; message?: string };

/**
 * The one function to design from scratch.
 *
 * Map this mutation onto the project's existing backend API, and map the response back
 * onto MutationOutcome. Suggested default HTTP-status mapping, unless the backend's own docs say
 * otherwise:
 *   2xx                              -> inspect the response body for per-operation failures;
 *                                       return success only if this mutation was applied
 *   network error / timeout / 5xx / 429 -> retryable_error
 *   401 / 403                        -> ask me: an expired token should be refreshed and retried,
 *                                       not discarded
 *   validation / conflict 4xx        -> fatal_error when the backend confirms a permanent rejection
 *   not found on repeated delete    -> success if the backend's retry semantics permit it
 *   other responses                  -> classify using the backend's documented contract
 */
async function callBackendApi(mutation: CrudEntry): Promise<MutationOutcome> {
  // mutation.op is 'PUT' | 'PATCH' | 'DELETE'
  // mutation.table is the client-side table name (map it to your API's resource)
  // mutation.opData holds the changed columns for PUT/PATCH
  // mutation.id is the row id
  throw new Error('TODO: call the backend API for this mutation, per the API surface found/described above');
}

// --- uploadData itself ---
//
// Pulls up to BATCH_SIZE pending transactions, then processes them in order. Within a
// transaction, mutations are applied one at a time so a single rejected mutation can be
// discarded without blocking the rest of that transaction or anything queued after it. The first
// retryable_error stops processing and throws. Anything not yet completed stays in the queue
// for the next attempt, which is what makes PowerSync retry.

async function uploadData(database: AbstractPowerSyncDatabase): Promise<void> {
  const transactions: CrudTransaction[] = [];

  for await (const transaction of database.getCrudTransactions()) {
    transactions.push(transaction);
    if (transactions.length >= BATCH_SIZE) break;
  }
  if (transactions.length === 0) return;

  for (const transaction of transactions) {
    for (const mutation of transaction.crud) {
      const outcome = await callBackendApi(mutation);

      if (outcome.status === 'success') {
        continue;
      }

      if (outcome.status === 'fatal_error') {
        // The backend said this exact mutation can never succeed as sent. Retrying it would block
        // the queue forever, so log it as an error and move on. The log line is how you find out
        // about the bug that caused it. If losing the mutation is not
        // acceptable, that is the dead-letter storage in the hardening list below.
        console.error('Discarding a mutation the backend rejected', mutation, outcome);
        continue;
      }

      // retryable_error: throwing makes the PowerSync SDK call uploadData again after a delay.
      // This transaction, and everything queued after it, is left uncompleted on purpose.
      throw new Error(`Retryable error uploading transaction: ${outcome.message ?? 'unknown'}`);
    }

    // Every mutation in this transaction is now applied or discarded, so the queue can move
    // past it.
    await transaction.complete();
  }
}
```

## Production hardening to raise with me

The implementation above is the minimum. Before you finish, ask which of these I want now, and leave the rest as named follow-ups in the connector's comments. There are many reasonable ways to build each, so match whatever the project already uses rather than inventing a mechanism:

- **A retry cap.** Without one, a backend that answers 5xx for a permanent failure blocks the queue forever. It needs a persisted counter per transaction, not an in-memory one, because the queue survives restarts.
- **Dead-letter storage** for rejected or retry-exhausted mutations, instead of log and discard. Store them somewhere a developer can inspect: a dead-letter table on the backend, or your error tracker.
- **Client status in your logging or error aggregation.** Ship upload failures with the mutation's table, operation and id, plus the SDK's sync status (connected, uploading, last upload error), so a stuck queue on one device is visible from the backend.
