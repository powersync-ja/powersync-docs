PowerSync client SDKs use SQLite, and apply reasonable defaults to optimize performance:

1. For all native targets, [write-ahead logging](https://www.sqlite.org/wal.html) (WAL) is enabled to support concurrent reads and writes. PowerSync also dispatches queries to multiple threads for parallelism. With the JavaScript web SDK, a WAL-like option is [available on Chromium browsers](/client-sdks/reference/javascript-web#2-opfs-based-alternatives).
2. SDKs also configure connections for performance by enabling a large page cache of around 50MB and setting `pragma synchronous = normal` to avoid frequent fsync operations.

## Debugging Query Performance

Slow queries can have two causes:

1. The query itself is slow, e.g. because it reads a lot of rows or uses unoptimized joins not backed by an index. The [Fixing Slow Queries](#fixing-slow-queries) section describes how these queries can be optimized.
2. The database is blocked. There can only be a single writer at a time, and the number of concurrent readers is bound by an option set when opening the database. So a query that appears slow might actually be fast, having run at an unfortunate time when the database was busy.

To understand the problem, having a trace of query runtimes available helps.

Enabling the `debugMode` flag in the [Web SDK](/client-sdks/reference/javascript-web) logs all SQL queries on the Performance timeline in Chrome's Developer Tools (after recording). This can help identify slow-running queries. With the Dart SDK, queries are logged to the [Performance View in DevTools](https://docs.flutter.dev/tools/devtools/performance) by default outside of release builds.

<Frame caption="Performance timeline in Chrome DevTools showing PowerSync query durations">
  ![Performance timeline showing PowerSync query durations](/images/resources/performance-timeline.png)
</Frame>

This includes:

- PowerSync queries from client code.
- Internal statements from PowerSync, including queries saving sync data, and begin/commit statements.

This excludes:

- The time spent waiting for the global transaction lock. It still includes all overhead in worker communication, so you generally won't see concurrent queries reflected in the trace.
- Internal statements from `powersync-sqlite-core`, used by the Sync client for Sync Stream bookkeeping.

Enable this mode when instantiating `PowerSyncDatabase`:

```js
export const db = new PowerSyncDatabase({
  schema: AppSchema,
  database: {
    dbFilename: 'powersync.db',
    debugMode: true // Defaults to false. To enable in development builds, use
      // debugMode: process.env.NODE_ENV !== 'production'
  }
});
```

If this reveals it took too long for a read connection to become available, consider increasing the size of the connection pool with the [maxReaders option](https://pub.dev/documentation/sqlite_async/latest/sqlite_async/SqliteOptions/maxReaders.html) (Dart), [readWorkerCount](https://powersync-ja.github.io/powersync-js/node-sdk/globals) (Node.js) or [additionalReaders](https://powersync-ja.github.io/powersync-js/web-sdk/globals#resolvedwebsqlopenoptions) (Web, only with `WASQLiteVFS.OPFSWriteAheadVFS`). The Swift and Kotlin SDKs always use four read connections; React Native uses five.

For contention on the write connection, note that the PowerSync client processes changes from the PowerSync Service in a single write transaction after they've been downloaded. Due to consistency requirements, this transaction cannot be split into multiple steps, and especially for a large initial sync it can hold a write lock for several seconds.

## Fixing Slow Queries

If a query itself is expensive and takes a long time to run, several options can improve performance. Some of these require a restructuring of your app's schema.

1. Where possible, filter on the `id` column of tables to reduce the number of rows read, which makes queries more efficient. When filtering on other columns of large tables, make sure these columns are covered by indexes declared in your app's schema.
2. For auto-updating watched queries on frequently-changed tables, queries might run very often. Watched queries should typically be cheap to run, as they otherwise risk blocking SQLite connections for too long. For more expensive queries that still need to be watched, consider increasing their throttle to run them less often.
3. By default, PowerSync tables are views over JSON data that extract columns by parsing from JSON each time a row is accessed. While SQLite has a cache for parsed JSON, this can still be inefficient for queries computing on columns. [Managed tables](#managed-tables) store data in SQLite columns instead, at the cost of slower schema changes.
4. If your app runs the same quick queries many times, SQLite spends part of each run reading the SQL and planning the query again. In the JavaScript Web and Dart SDKs, a [prepared statement cache](#prepared-statement-cache) keeps recently planned queries so that SQLite can reuse them.
5. In the JavaScript SDKs, you can replace regular watched queries with [High Performance Diffs](/client-sdks/high-performance-diffs). These use triggers internally to report only changed rows back to your app.

### Prepared Statement Cache

For cheap statements that run frequently, the cost of preparing a statement (making SQLite parse the SQL text and come up with a query plan based on available indexes) can make up a substantial chunk of the total query runtime.

In the JavaScript Web and Dart SDKs, enable a cache of prepared statements when opening the database:

<CodeGroup>

```typescript TypeScript
const db = new PowerSyncDatabase({
  schema,
  database: {
    dbFilename: 'my_database.db',
    // Cache up to 64 prepared statements
    preparedStatementsCache: 64,
  },
});
```

```dart Dart
final db = PowerSyncDatabase(
  schema: Schema([...]),
  path: 'my_database.db',
  sqliteOptions: SqliteOptions(
    // Cache up to 64 prepared statements
    preparedStatementCacheSize: 64,
  ),
);
```

</CodeGroup>

In both SDKs, each connection uses its own independent cache and the maximum size applies to those caches. When the cache is full, the least-recently-used statement is evicted.

For more information, see the `preparedStatementsCache` option [for JavaScript](https://powersync-ja.github.io/powersync-js/web-sdk/globals#webspecificopenoptions) or [for Dart](https://pub.dev/documentation/powersync/latest/sqlite_async/SqliteOptions/preparedStatementCacheSize.html).

## Managed Tables

<Note>
  **Availability**

  Managed tables are currently in [alpha](/resources/feature-status), so their API may change based on feedback. They were introduced in the following versions of our client SDKs:

  - **JavaScript** (React Native: `2.3.4`, Web: `2.6.0`, Node.js: `1.2.1`, Capacitor: `0.9.5`)
  - **Dart**: Version `2.6.0`.
  - **Kotlin**: Version `1.16.0`.
  - **Swift**: Version `1.17.0`.
  - **.NET**: Not supported yet.
  - **Rust**: Version `0.2.0`.
</Note>

By default, each table in your client-side schema is a **managed view**. PowerSync stores synced rows as [JSON in an internal table](/architecture/client-architecture#client-side-schema-and-sqlite-database-structure) and creates a SQLite view that extracts your columns from it. Queries on the view decode the JSON of every row they read.

A **managed table** stores rows in a SQLite table with a column for each column in your schema, so queries read values directly. You query and write to it with the same SQL statements as a managed view. PowerSync still creates and migrates the table, and it still adds local writes to the upload queue.

In our tests on a table with 1 million rows, `SELECT *` queries were about 2x faster on a managed table. Filtering, sorting or aggregating on a column without an index was about 6x faster. The database file was about 20% smaller. How much storage you save depends on your data. Rows with large text values save less, because the JSON overhead is a smaller part of each row.

These numbers come from simulated benchmarks, so results in your app depend on your data and queries. If you try managed tables, let us know how they perform in your app.

### Choosing a Table Type

The table types differ in two ways: who creates and migrates the table, and whether queries read JSON or SQLite columns.

|  | Managed views (default) | Managed tables | Raw tables |
| --- | --- | --- | --- |
| Created and migrated by | PowerSync | PowerSync | You |
| Queries read | JSON, through a view | SQLite columns | SQLite columns |
| Schema changes | Near-instant | Take longer as the table grows | Migrations you write |

- **Managed views:** Use these by default: schema changes are near-instant, because PowerSync only re-creates the views. Queries that read many rows of a large table can be slower than on a managed table.
- **Managed tables (alpha):** Switch a table to a managed table if its queries are measurably too slow. This is typically a large table that you filter, sort or aggregate on columns without an index. You set this per table, so the other tables can stay managed views. Schema changes on a managed table take longer as the table grows.
- **Raw tables:** Use [raw tables](/client-sdks/advanced/raw-tables) when you want full control over the SQLite table, for example to add foreign keys, custom triggers or expression indexes, or to use a library such as [Room](/client-sdks/orms/kotlin/room) that manages the schema. You then create and migrate the table yourself.

### Enabling Managed Tables

Set the `direct` flag on the table definition. The flag name refers to queries reading the table directly, with no view in between.

<CodeGroup>

```typescript TypeScript
const schema = new Schema({
  users: new Table({ name: column.text }, { direct: true })
});
```

```dart Dart/Flutter
const schema = Schema([
  Table.direct('users', [Column.text('name')])
]);
```

```kotlin Kotlin
val schema = Schema(
  Table("users", listOf(Column.text("name")), direct = true)
)
```

```swift Swift
let schema = Schema(
  Table(name: "users", columns: [.text("name")], direct: true)
)
```

```rust Rust
let mut schema = Schema::default();
schema
  .tables
  .push(Table::create("users", vec![Column::text("name")], |tbl| {
    tbl.direct = true
  }));
```

</CodeGroup>

Before you switch a table, check how managed tables differ from managed views:

- **Column types:** Managed views cast each value to the column type in your schema. Managed tables store values with the type they were synced or written with, so a value synced as text into an `integer` column stays text. Filters and sorting on that column can then return different results than on a managed view.
- **View names:** Managed tables aren't views, so you can't set the `viewName` option. If you use `viewName` to [move data from a local-only table to a synced table](/client-sdks/advanced/local-only-usage#moving-data-to-synced-tables), keep that table as a managed view.
- **High Performance Diffs:** In the JavaScript SDKs, [High Performance Diffs](/client-sdks/high-performance-diffs) don't support managed tables yet. Keep tables that you watch with High Performance Diffs as managed views.

### Migrations

To switch a table between a managed view and a managed table, change the `direct` flag. PowerSync moves the existing rows when it applies the new schema, without downloading them again.

When you add or remove columns, PowerSync runs the `ALTER TABLE` statements for you. These changes process every row in the table, whereas a managed view only needs its view re-created. In our tests on a table with 1 million rows, switching between a managed view and a managed table took a few seconds. Adding or dropping a column took up to about a second. On a managed view, both are near-instant.

A new column on a managed table is `NULL` until the next completed sync. On a device that is offline after an app update, the column stays `NULL` until the device reconnects. After the sync, PowerSync fills the column from synced data that is already on the device, so nothing downloads again. This copy adds to the time that adding a column takes.
