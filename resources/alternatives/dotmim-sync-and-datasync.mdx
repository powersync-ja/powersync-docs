[Dotmim.Sync](https://dotmimsync.readthedocs.io/) is an open-source .NET library that syncs rows between a server database and client databases. The client app starts each sync session by calling `SynchronizeAsync()`. On SQL Server, Dotmim.Sync detects changes with SQL Server Change Tracking, or with its own triggers and tracking tables.

[CommunityToolkit.Datasync](https://communitytoolkit.github.io/Datasync/) is part of the .NET Community Toolkit and was previously known as Azure Mobile Apps. Your ASP.NET Core API hosts its table controllers. The app uses an EF Core `OfflineDbContext` that stores data in SQLite and sends or fetches changes when the app calls `PushAsync()` or `PullAsync()`.

[PowerSync](/intro/powersync-overview) syncs data from your backend database into a SQLite database inside your app. The app reads and writes that local database directly, so it responds instantly and keeps working without a network connection. PowerSync syncs changes in both directions when the app is connected. On SQL Server, the PowerSync Service reads changes through Change Data Capture (CDC).

<Note>
  This document compares Dotmim.Sync 1.3.0, CommunityToolkit.Datasync 10.2.0, PowerSync Service 1.28.3, and version 1.0.1 of the PowerSync .NET SDK (`PowerSync.Common`).
</Note>

This comparison is based on each product's documentation and source code, and on building the same SQL Server, ASP.NET Core, and .NET MAUI app with each of the three tools. See [Migrating a SQL Server and .NET MAUI App to Offline-First](/migration-guides/sql-server-maui) for the PowerSync version of that app.

## How Server Changes Are Captured

All three tools pick up writes made directly with SQL, for example by a back-office system, with no change to that system.

### PowerSync

The PowerSync Service reads changes from SQL Server through [Change Data Capture (CDC)](https://learn.microsoft.com/en-us/sql/relational-databases/track-changes/about-change-data-capture-sql-server). See [SQL Server](/configuration/source-db/setup#sql-server) for the setup steps.

### Dotmim.Sync

Dotmim.Sync's `SqlSyncChangeTrackingProvider` uses SQL Server [Change Tracking](https://dotmimsync.readthedocs.io/ChangeTracking.html). Its other SQL Server provider, `SqlSyncProvider`, uses triggers and tracking tables instead.

### Datasync

Datasync tracks changes with metadata on each row, and the client pulls the rows whose `UpdatedAt` is later than the newest row it already has. See [Azure SQL and SQL Server](https://communitytoolkit.github.io/Datasync/in-depth/server/db/azuresql/) for the trigger that keeps `UpdatedAt` current.

Datasync doesn't send hard deletes to devices. To sync deletes, you [enable soft delete](https://communitytoolkit.github.io/Datasync/in-depth/server/) and run a separate job to purge deleted rows.

## How Data Is Stored on the Client

### PowerSync

The PowerSync client SDK manages a SQLite database on the device. Your app queries it with SQL. [Watch queries](/client-sdks/watch-queries) rerun when a local write or a sync changes a table that the query reads, so the UI updates without a manual reload.

### Dotmim.Sync

Dotmim.Sync creates a SQLite database that mirrors the server tables on the first sync. Your app queries it with `Microsoft.Data.Sqlite`. Dotmim.Sync has no watch queries, so your app queries again after each sync and each local write.

### Datasync

Datasync stores data in SQLite through EF Core, and your app queries the `OfflineDbContext` with LINQ. Your entities are typed classes on both the server and the client. Datasync has no watch queries.

## How Writes Work

All three tools save the user's change locally first, so the app shows it immediately. They differ in where the change arrives on your server.

| Tool | Where changes arrive | Where your business rules run |
| --- | --- | --- |
| **PowerSync** | Your existing API endpoint, called from your `uploadData()` function | Your existing endpoint |
| **Dotmim.Sync** | A sync endpoint in your API, as changed rows | A server interceptor (`OnRowsChangesApplying`) |
| **Datasync** | A table controller in your API, one request per change | An `IAccessControlProvider` |

If your existing endpoint enforces business rules, either alternative needs the same rules again in its server hook.

{/* Datasync ordering: OperationsQueueManager.GetQueuedOperationsAsync has no ORDER BY in 10.2.0, and the docs warn that ParallelOperations > 1 "MAY be executed on the remote service out of order". */}

Each tool has its own detail to handle:

- **Dotmim.Sync:** Uploads are idempotent upserts keyed by the row's primary key, so a retried sync doesn't create a duplicate row. Dotmim.Sync detects conflicts per row and resolves them with `ServerWins` by default. See [Conflicts](https://dotmimsync.readthedocs.io/Conflict.html).
- **Datasync:** The queue doesn't push operations in the order the changes were made. A parent change and a child change can arrive as separate requests, in the wrong order. Datasync has built-in optimistic concurrency: the server checks `Version` with `If-Match`, and you can configure `ClientWinsConflictResolver`, `ServerWinsConflictResolver`, or your own `IConflictResolver`. A retried create gets a 409 from the server. Without a conflict resolver, that operation stays failed.
- **PowerSync:** Your endpoint decides how to handle conflicts, so the rule lives in your own code. With the simplest endpoint, the result is per-field last-write-wins, because each `PATCH` carries only the changed columns. A retry sends the whole transaction again, so your endpoint must be safe to repeat. See [Write Path Concepts](/handling-writes/write-path/concepts#retryable-errors) and [Handling Update Conflicts](/handling-writes/handling-update-conflicts).

## Rejected Writes and Stuck Queues

Sometimes your backend permanently refuses a write. A business rule says no, or the record changed on the server while the device was offline. Any of the three tools can get stuck if the app treats a permanent rejection as a temporary error. The difference is what each tool does by itself, and what you build to recover.

### PowerSync

Your `uploadData()` function classifies each response from your API. On a permanent rejection, it logs the error, records the reason, and calls `complete()` so the upload queue moves on. Your API returns the reason in a 2xx response body, or writes it to a table that syncs back to the client.

After the upload queue is empty and the client has synced, the client SDK replaces the local data with the synced copy. The rejected change disappears from the device with no extra code. See [How Changes Are Rolled Back](/handling-writes/write-path/concepts#how-changes-are-rolled-back).

If `uploadData()` throws on a permanent rejection instead, the transaction is **blocked**. Later writes from that device can't upload, and the sync status shows an `uploadError` on every attempt. See [Blocked Transactions](/handling-writes/write-path/concepts#blocked-transactions).

### Dotmim.Sync

Your server interceptor can reject a row in one of two ways:

- **Drop the row.** The sync reports success, and no reason reaches the device. The rejected row stays in the device's local database, because the server never stored it.
- **Throw an exception.** The reason reaches the client in an `HttpSyncWebException`, but the server rolls back the whole sync. Every later sync fails in both directions until the server accepts the row.

To recover without stopping sync, drop the row and tell the device yourself, for example with a table of rejections that syncs down to each user. A sync with `SyncType.ReinitializeWithUpload` removes the rejected local rows, because it downloads all rows again. See [Interceptors](https://dotmimsync.readthedocs.io/Interceptors.html). For errors that the database raises while it applies a row, such as a constraint violation, see `ErrorResolutionPolicy` in [Errors](https://dotmimsync.readthedocs.io/Errors.html).

{/* Dotmim.Sync: dropping rows is the documented use of OnRowsChangesApplying ("Intercepting rows"), and SyncType.ReinitializeWithUpload is documented under SyncOperation, both on the Interceptors page. The hands-on build confirmed that ReinitializeWithUpload removes rows that the server never stored. */}

### Datasync

When the server rejects a pushed operation, `PushAsync()` reports it in `PushResult.FailedRequests`, and the operation stays in the queue as failed. Every later push sends it again. Datasync's conflict resolvers run only for 409 and 412 version conflicts, so they don't clear other rejections.

{/* Datasync: ServiceResponse.IsConflictStatusCode is "StatusCode is 409 or 412", and OperationsQueueManager.PushOperationAsync calls the resolver only while that is true (10.2.0). */}

`PullAsync()` refuses to pull any entity type that still has a queued operation, including a failed one:

```text
DatasyncException: There are still pending operations in queue for table '<Entity>'.
```

As a result, one rejected write stops the device from receiving server changes for that table. This check is deliberate. See [`OfflineDbContext.PullAsync`](https://github.com/CommunityToolkit/Datasync/blob/10.2.0/src/CommunityToolkit.Datasync.Client/Offline/OfflineDbContext.cs). A rejection can happen after the device was offline, or online when two devices update the same record.

To recover, your app removes the rejected operation from `DatasyncOperationsQueue`, undoes the local change itself, and pulls again. The library doesn't keep the previous value. The docs' [Re-synchronizing All Data](https://communitytoolkit.github.io/Datasync/in-depth/client/#re-synchronizing-all-data) recipe does this for a whole table, which also discards the user's other unsynced changes. See also the maintainer's guidance in [issue #248](https://github.com/CommunityToolkit/Datasync/issues/248).

{/* No previous value: https://github.com/CommunityToolkit/Datasync/discussions/456 (undoing a local change isn't supported; discard and pull again). */}

{/* Related, not for the page: https://github.com/CommunityToolkit/Datasync/issues/578 (a timed-out push left its operation queued, so the next PullAsync threw the same error) was fixed in 10.2.0. */}

## When Data Syncs

All three tools support offline reads and writes, and keep pending writes across app restarts.

### PowerSync

While the app is connected, the PowerSync Service streams changes to it, and the app doesn't need to do anything. This includes writes made directly with SQL, which CDC captures. When the connection returns, the client SDK uploads queued writes by itself.

### Dotmim.Sync and Datasync

Dotmim.Sync and Datasync don't push changes to the device. A sync reads SQL Server directly, so it returns current data with no replication delay. The device sees server changes only when the app syncs, for example at startup, on pull-to-refresh, or when a page opens. Datasync's [real-time tutorial](https://communitytoolkit.github.io/Datasync/tutorial/server/part-5/) sends SignalR messages from `PostCommitHookAsync`. That hook runs only for writes through the table controllers, not for writes made directly with SQL.

Queued writes upload only when the app syncs.

## Auth and Per-User Data

### PowerSync

PowerSync clients connect with a JWT. [Sync Streams](/sync/streams/overview) use claims from the token, such as `auth.user_id()`, to choose the rows each client receives. When a row leaves a user's streams, for example because the user loses access, the client SDK removes it from the device. Your backend authorizes writes when `uploadData()` sends them. If your API already issues RS256 tokens and publishes a JWKS, the PowerSync Service can verify the same tokens. See [Authentication](/configuration/auth/overview).

### Dotmim.Sync

Dotmim.Sync's sync endpoint is a normal controller in your API, protected with `[Authorize]`. See [Web Security](https://dotmimsync.readthedocs.io/WebSecurity.html). Per-user rows come from setup [filters](https://dotmimsync.readthedocs.io/Filters.html) with parameters, such as a user ID.

<Warning>
  The client sends Dotmim.Sync's filter parameters. Set them on the server from the token in an interceptor, such as `OnHttpGettingRequest`, and always overwrite the value that the client sent. Otherwise, a client can request another user's rows by sending that user's ID.
</Warning>

{/* Dotmim.Sync's "Hook Bearer token" example (https://dotmimsync.readthedocs.io/Interceptors.html) adds the parameter only when the client did not send one. */}

Filters don't apply to uploads, so your interceptor also checks that the user owns each uploaded row.

### Datasync

Datasync's table controllers use `[Authorize]`. `IAccessControlProvider.GetDataView()` limits which rows a user can read. `IsAuthorizedAsync()` and `PreCommitHookAsync()` control writes. See [Configure Access Permissions](https://communitytoolkit.github.io/Datasync/in-depth/server/#configure-access-permissions).

On the client, Datasync's [`GenericAuthenticationProvider`](https://communitytoolkit.github.io/Datasync/in-depth/client/auth/) gets a new token only when the cached one is near expiry. A 401 response doesn't trigger a new token. If you rotate your signing key, each sync fails until the cached token nears expiry or the app calls `LoginAsync()`.

{/* GenericAuthenticationProvider (10.2.0) refreshes when now >= ExpiresOn - RefreshBufferTimeSpan (default 2 minutes) and has no 401 handling in SendAsync. */}

## Schema Changes

Adding a nullable column to a synced table takes different steps in each tool.

### PowerSync

You run `ALTER TABLE`, add a new CDC capture instance for the table, and redeploy your Sync Config. The redeploy reprocesses the data, and the previous deployment serves clients until the new one is active. Installed apps keep working, because the client-side schema is a view over schemaless data. To use the column, the app adds it to its client-side schema. See [SQL Server Specifics](/maintenance-ops/implementing-schema-changes#sql-server-specifics).

### Dotmim.Sync

You re-provision the server scope in code. After that, apps that haven't upgraded can still download changes, but can't upload them. The [Provision](https://dotmimsync.readthedocs.io/Provision.html) docs say that each client must migrate its local schema and re-provision too. An app release must therefore reach devices before you change the server. Alternatively, you can use a new scope for each schema version.

### Datasync

On the server, a schema change takes three steps: `ALTER TABLE`, add the property, and redeploy. On the device, `EnsureCreated()`, which the Datasync samples use, doesn't change an existing database, and the Datasync docs have no guidance on client migrations. An upgraded app fails with `no such column` errors until it uses EF Core migrations. Rows that the device pulled before the change get the new column only when they change again on the server.
