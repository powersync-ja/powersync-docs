After you've [instantiated](/intro/setup-guide#instantiate-the-powersync-database) the client-side PowerSync database, you call `connect()` on it. The client SDK then downloads data from the [PowerSync Service](/architecture/powersync-service) into the client-side SQLite database, and uploads local mutations to your backend. For this, it uses two parts that you implement:

| Part | Used for | Description |
| --- | --- | --- |
| **Authenticator** | Downloading data | Its `resolveCredentials()` method returns a JWT that the PowerSync Service accepts. You pass the authenticator to `connect()` together with your _instance URL_, the URL of your PowerSync Service instance. See [Authenticator](#authenticator). |
| **Mutation uploader** | Uploading mutations | A function that uploads the mutations in the upload queue to your write API. These docs call it `uploadData()`. See [Mutation Uploader](#mutation-uploader). |

When you're getting started, we recommend that you focus on the read path first: implement the authenticator, connect download-only, and check that synced data reaches your app. Add the uploader when your app starts to write data. You can connect in three ways:

- **Download-only:** Pass the instance URL and the authenticator. Use this while your app only reads synced data. If the app writes to the local database while it's connected download-only, synced data stops updating: the SDK can't apply new data while mutations wait in the upload queue, and it reports a download error on the sync status. Add the uploader before your app writes.
- **Downloads and uploads:** Pass the instance URL, the authenticator and the uploader.
- **Upload-only:** Pass only the uploader. The SDK uploads mutations to your backend and doesn't connect to the PowerSync Service.

Each `connect()` call replaces the previous one. For example, connecting download-only and then upload-only leaves the database in upload-only mode. For the code in each SDK, see [Connect for Downloads or Uploads Only](/client-sdks/usage-examples#connect-for-downloads-or-uploads-only).

<Note>
  The authenticator and mutation uploader require `@powersync/web` 2.6.0, `@powersync/react-native` 2.4.0, `@powersync/node` 1.3.0, `@powersync/capacitor` 0.10.0, Dart/Flutter 2.6.0, Kotlin 1.16.0, Swift 1.17.0 or Rust 0.2.0, or later. The .NET SDK and the Tauri plugin don't support them yet. Until they do, use a [backend connector](#backend-connector) with those SDKs.
</Note>

## Authenticator

The SDK calls `resolveCredentials()` on your authenticator to get a JWT for the PowerSync Service. How you get the JWT depends on your authentication setup:

- **Development:** Return a [development token](/configuration/auth/development-tokens).
- **JWTs from your authentication provider:** Some providers issue JWTs that PowerSync can verify directly. Return the JWT from your app's authentication session. See [Common Authentication Providers](/configuration/auth/overview#common-authentication-providers).
- **Custom authentication:** Request a JWT from your backend. See [Custom Authentication](/configuration/auth/custom).

See [Authentication Setup](/configuration/auth/overview) for more details on JWT authentication.

### When `resolveCredentials()` is Called

Cache the token in your authenticator: return the cached token from `resolveCredentials()`, and clear the cache in `invalidateCredentials()`. The SDK <Tooltip tip="Only the JavaScript SDKs currently cache the token themselves.">usually</Tooltip> doesn't cache the token, and it calls `resolveCredentials()` often, for example on every reconnect. If your authentication library already caches its token, you can return that token instead.

When the SDK needs a new token, it calls `invalidateCredentials()` and then `resolveCredentials()`. This happens when:

1. **The token is about to expire:** The PowerSync Service sends periodic keepalive messages that include the remaining lifetime of the current JWT. When the token has **30 seconds or less** remaining, the SDK gets a new token in the background and reconnects with it.
2. **The token has expired:** If the token expires, for example while the device is offline, the SDK gets a new token when it reconnects.
3. **The Service rejects the token:** If the PowerSync Service responds with a `401` status, the SDK gets a new token on the next connection attempt.

For a JWT with a 1-hour expiry, the SDK typically needs a new token **about once per hour**.

### Recommended JWT Expiry Duration

A JWT expiry (TTL) of **5 to 60 minutes** works well with PowerSync:

- **Shorter JWTs (5–15 minutes):** More secure with minimal overhead, since the SDK only needs a new token when the current one is near expiry.
- **Longer JWTs (30–60 minutes):** Fewer token requests and a simpler backend implementation.

The SDK gets new tokens regardless of the TTL, as long as `resolveCredentials()` can return a valid token when called.

Avoid JWTs with a TTL shorter than 30 seconds. The SDK gets a new token when 30 seconds or less remain, so a shorter TTL skips that step and always goes through the expired-token reconnection.

### Token Expiry While Offline

If the JWT expires while the device is offline, the SDK gets a new token from `resolveCredentials()` when connectivity is restored.

The JWT only authenticates the client SDK's connection to the PowerSync Service. When it expires, your app's own sign-in session (for example with Supabase Auth or Firebase Auth) is not affected. That session has its own lifecycle and refresh mechanism.

## Mutation Uploader

The client SDK records every mutation in an _upload queue_ and calls your mutation uploader, `uploadData()`, to upload the queued mutations to your write API. If `uploadData()` throws, the SDK retries it. To pick how to upload mutations, see [Choosing Your Implementation](/handling-writes/write-path/choosing-your-implementation).

### When `uploadData()` is Called

The client SDK calls `uploadData()` automatically - you never call it directly. It is invoked in the following scenarios:

1. **After your app writes** - Any `INSERT`, `UPDATE`, or `DELETE` on a PowerSync table adds an entry to the internal upload queue (the `ps_crud` table). The SDK monitors this table for changes and triggers `uploadData()` shortly after. See [How Local Writes Are Detected](#how-local-writes-are-detected) below for details on the underlying mechanism.
2. **On initial connection / reconnection** - When `connect()` establishes (or re-establishes) a sync stream and the first message is received from the PowerSync Service, the SDK triggers `uploadData()` to flush any writes that were made while offline or disconnected.
3. **After an error, with retry** - If `uploadData()` throws an error, the SDK waits for a configurable <Tooltip tip="retryDelayMs in JavaScript, retryDelay in Kotlin, Swift and Dart">retry delay</Tooltip> (default: 5 seconds) and then retries. This continues until the upload succeeds or the sync stream is disconnected.

#### How Local Writes Are Detected

By default, each PowerSync-managed table is exposed in SQLite as a **view** with `INSTEAD OF INSERT/UPDATE/DELETE` triggers (generated by the [PowerSync SQLite core extension](https://github.com/powersync-ja/powersync-sqlite-core) when your [client-side schema](/intro/setup-guide#define-your-client-side-schema) is applied). When you write to a PowerSync table, those triggers do two things atomically:

1. Apply the change to the [underlying `ps_data__<table>` table](/architecture/client-architecture#client-side-schema-and-sqlite-database-structure).
2. Append an entry to `ps_crud` describing the mutation (see [Write Operations](/handling-writes/write-path/concepts#write-operations) for the entry format).

Because both happen in the same transaction, the upload queue can never get out of sync with local data. ([Raw Tables](/client-sdks/advanced/raw-tables#capture-local-writes-with-triggers) preserve this guarantee, except you create the triggers yourself, typically via the `powersync_create_raw_table_crud_trigger` helper.)

The SDK then detects new `ps_crud` entries by subscribing to SQLite's table-update notifications, filtered for changes to `ps_crud`. This is the same mechanism that powers reactive [watch queries](/client-sdks/watch-queries). When a change is observed, the SDK schedules an `uploadData()` call subject to the configured [throttle interval](#throttling).

The mechanism is consistent across all PowerSync SDKs (JavaScript, Dart, Kotlin, Swift, .NET, Rust), since the triggers and `ps_crud` table are defined by the shared PowerSync SQLite core extension.

#### Upload Loop Behavior

The SDK calls `uploadData()` in a **loop** - not just once per trigger. After each successful `uploadData()` call, the SDK checks whether there are more items in the upload queue. If there are, it calls `uploadData()` again immediately. The loop continues until the queue is empty. This means your `uploadData()` implementation only needs to process one batch (or one transaction) per call.

Once the queue is empty, the SDK updates an internal write checkpoint used for [consistency](/architecture/consistency) tracking.

#### Throttling

To avoid excessive calls, upload triggers are **throttled**. Mutations in quick succession (e.g., multiple `INSERT` statements) are coalesced so that `uploadData()` is invoked at most once per throttle interval. If an upload is already in progress when a new write occurs, the SDK will trigger another upload after the current one completes.

The default throttle interval varies by SDK:

| SDK | Default | Option Name |
| --- | --- | --- |
| JavaScript / React Native / Node / Capacitor / Tauri | 1,000 ms | `crudUploadThrottleMs` |
| Kotlin | 1,000 ms | `crudThrottle` (in `SyncOptions`) |
| Swift | 1 second | `crudThrottle` (seconds) |
| .NET | 1,000 ms | `CrudUploadThrottleMs` |
| Dart / Flutter | 10 ms | `crudThrottleTime` |

You can configure the throttle interval in the options when you call `connect()`:

<CodeGroup>

```typescript TypeScript
await db.connect({
  ...
  crudUploadThrottleMs: 500
});
```

```dart Dart/Flutter
db.connect(
  ...
  options: SyncOptions(
    crudThrottleTime: Duration(milliseconds: 500),
  ),
);
```

```kotlin Kotlin
database.connect(
    ...
    options = SyncOptions(crudThrottle = 500.milliseconds),
)
```

```swift Swift
try await database.connect(
  ...
  options: ConnectOptions(crudThrottle: 0.5) // seconds
)
```

```csharp .NET
await database.Connect(connector, new PowerSyncConnectionOptions(
  crudUploadThrottleMs: 500
));
```

</CodeGroup>

#### Error Handling

<Warning>
  If your `uploadData()` throws an error, the SDK keeps **retrying** the same upload while it's connected, and every later mutation in the upload queue waits behind it. Throw only for errors that a retry can fix. See [What Happens When a Write Fails](/handling-writes/write-path/concepts#what-happens-when-a-write-fails) for how to handle each kind of failure.
</Warning>

When `uploadData()` throws an error:

1. The SDK logs the error and updates the sync status with an `uploadError`.
2. It waits for the retry delay (default: 5 seconds).
3. It retries the upload from the beginning of the queue.
4. If the sync stream disconnects during the retry wait, the upload loop exits and will resume when the connection is re-established.

#### Stalled Upload Queue Detection

If the SDK detects that the same CRUD entry is at the front of the queue across consecutive upload iterations (i.e., `uploadData()` returned without error but didn't call `.complete()` on the batch or transaction), it logs a warning:

> _"Potentially previously uploaded CRUD entries are still present in the upload queue. Make sure to handle uploads and complete CRUD transactions or batches by calling and awaiting their [.complete()] method. The next upload iteration will be delayed."_

After logging this warning, the SDK **throws an internal error**, which causes it to enter the retry delay path (default: 5 seconds) before attempting the upload again. This prevents a tight loop when `uploadData()` consistently fails to process entries.

This typically means your `uploadData()` implementation is not calling `.complete()` after successfully processing entries. Always call `.complete()` on the `CrudBatch` or `CrudTransaction` to remove processed entries from the queue.

<Tip>
  While the device is offline, writes stay in the upload queue. The client SDK uploads them after the device reconnects.
</Tip>

## Backend Connector

A _backend connector_ is the previous way to connect: a single object that you pass to `connect()`. Its `fetchCredentials()` method returns a JWT and the instance URL, and its `uploadData()` method uploads mutations. Existing backend connectors keep working in every SDK except Rust, which removed them in version 0.2.0. We plan to deprecate backend connectors in a future release, so use an authenticator and a mutation uploader in new code. This section helps you migrate an existing connector.

To migrate a backend connector:

- Move the token logic from `fetchCredentials()` into `resolveCredentials()`, which returns only the token. Pass the instance URL to `connect()` instead.
- Pass your `uploadData()` to `connect()` as the mutation uploader. Its parameters can <Tooltip tip="In the JavaScript SDKs, the uploader receives an options object with a database field instead of the database itself.">differ slightly</Tooltip>.
- Cache the token in your authenticator and clear the cache in `invalidateCredentials()`. The SDK caches what `fetchCredentials()` returns, but <Tooltip tip="Only the JavaScript SDKs currently cache what resolveCredentials() returns.">usually</Tooltip> not what `resolveCredentials()` returns. See [When `resolveCredentials()` is Called](#when-resolvecredentials-is-called).
- If your backend connector handles [checkpoint requests](/client-sdks/checkpoint-requests), move `postCheckpointRequest()` to your authenticator. See [Authenticator Changes](/client-sdks/checkpoint-requests#authenticator-changes).

### When `fetchCredentials()` is Called

For a backend connector, the SDK caches what `fetchCredentials()` returns. It calls `fetchCredentials()` in the same cases as `resolveCredentials()`: on the first connection, when the token is about to expire, after it has expired, and after a `401` response. Return a new token whenever `fetchCredentials()` is called, even if the previous one hasn't expired yet.
